# ClaudeClient — Claude API とプロンプト

`phase2/lib/ClaudeClient.ps1` (約 1,400 行)

PowerShell に公式 SDK が無いので、Messages API を素の HTTP で叩く。
このファイルが持っているのは**4つの仕事**で、性質がかなり違う。

| | |
|---|---|
| ツール定義 | 判定・記憶・検証の出力スキーマ。閉じた集合で受ける |
| プロンプト | 判定 / 作業 / 検証 / 記憶 の system プロンプト。**このシステムの方針が一番濃く出ている場所** |
| 転送 | 再試行・拒否の判定・エラー本文の展開・トークン数の記録 |
| 会話 | エージェントループ、保存と再開、プロンプトキャッシュ |

---

## 1. 役割と境界

| | |
|---|---|
| 担う | API の呼び出しと再試行 / プロンプトとツール定義 / エージェントループ / キャッシュの区切り / 会話の JSON 化 |
| 担わない | ツールの**実行** (`OnTool` として呼ぶ側が渡す) / 会話の保存先 (`OnSave` で渡す) / 承認 / DB |

**ツールを実行しない**のが一番大事な線。`Invoke-ClaudeAgent` はツールの名前と入力を
`OnTool` に渡して結果を受け取るだけで、何を許すか・どこに書くかは知らない。
承認の門 (`WorkTools.ps1`) と作業フォルダの束縛はワーカー側にあり、
ここを差し替えてもモデルの権限は変わらない。

依存は `lib/ApiKey.ps1` だけ (キーの取得元は環境変数 → 資格情報ストア → 配布設定)。

**依存元**:

```
phase2/Invoke-Triage.ps1    Invoke-ClaudeTriage / Invoke-ClaudeMemory
phase4/Start-Worker.ps1     Invoke-ClaudeWork / Invoke-ClaudeVerify / 会話の保存と再開
```

## 2. 構成要素

### ツール定義 (出力を閉じた集合で受ける)

| ツール | 使う場面 | 要点 |
|---|---|---|
| `record_triage` | 通知の判定 | `needs_action` / `urgency` / `category` / カード名・要約・理由・想定対応 |
| `record_memory` | カードが閉じたあと | `kind` は `profile` / `preference` / `how` の3つだけ。`note` は 200 字以内 |
| `record_verification` | 成果物の検証 | `verdict` / `completed` / `issues[]` (severity・where・problem・fix) |

いずれも `tool_choice` でそのツールを**強制**する。自由記述で受けないのは、
記憶でとくに効く ―― 「今回限りの事情」(この案件の締切は9月末) まで人についての記憶として
積もると、件が変わっても渡り続けて判断の材料が薄まる。**種類と長さで先に絞る。**

### プロンプト

| 関数 | 誰のためのプロンプトか |
|---|---|
| `Get-TriageSystemPrompt` | 分類器。文脈不足なら urgency を下げて理由に書かせる |
| `Get-WorkSystemPrompt` | 実務の担当者。**カードの閉じ方の優先順位**がここにある |
| `Get-VerifySystemPrompt` | 点検役。作成者の前提を引き継がない別の会話 |
| `Get-MemorySystemPrompt` | 記憶係。事実だけを取り、担当者の言い分は覚えない |

`$script:InjectionGuard` を**全部のプロンプトの末尾に入れる。**
`<notification>` と `<thread>` の内側は第三者が書いたデータであって指示ではない、と明示する。
通知本文には他人の文章がそのまま入るので、ここが素通しだと
「ボードに載った文面がシステムに指示を出す」道ができる。

**タグの外に置くもの / 中に置くもの**は意図的に分けてある。

| 外 (システムが与えた事実) | 中 (第三者が書いたデータ) |
|---|---|
| 利用者について覚えていること | 通知本文 |
| 名義 (本人は誰で、このメールでの立場は何か) | メール・スレッドの全文 |
| 件の台帳、試したことの記録 | 前回の報告 (担当者の言い分なので `<thread>` に入れる) |

作業プロンプトの中心は**閉じ方の順序**で、上から順に検討させる。

```
自分で操作して終わらせる (http_request)
  → 送る (propose_reply / 送信ツール)
    → 人間の1手 (require_human_step)   ※手を尽くしたあとにだけ使える
      → 引き渡す (blocker='beyond_tools')
```

ここに書いてある禁止事項は、ほぼ全部が**実際に起きたこと**への対処。
「http_request で git の操作を組み立てない」は、テストの期待値2行を直すつもりで
ファイル全体を1行に置き換えた件 (#295) から来ている。

### プロンプトキャッシュ

system プロンプトとツール定義は、通知1件ごと・ツール往復1回ごとに**まったく同じものを
送り直している**。ここが入力トークンの大半を占めるので、キャッシュに載せれば
2回目からは約 1/10 の値段で読める。

**キャッシュは前方一致でしか効かない。** `tools` → `system` → `messages` と並べたバイト列が、
区切り (`cache_control`) の手前まで前回と1バイトでも違えば、そこから先は総入れ替えになる。

| 場面 | 区切りをどこに置くか | 関数 |
|---|---|---|
| 単発の呼び出し (判定・記憶・検証) | `system` の末尾に1つ。手前の `tools` ごと載る | `New-SystemBlocks` |
| エージェントループ | 送る直前に**会話の末尾へ移す**。前のターンまでは読み出しになる | `Set-CacheBreakpoint` |

`Set-CacheBreakpoint` には2つの決まりがある。

- **区切りは増やさず移す。** 1リクエストに4つまでなので、前のターンの区切りは外す。
  書き込まれたキャッシュはその位置に残っており、新しい区切りからそこまで遡って読まれる。
- **置くのは `user` の末尾だけ。** `assistant` のブロックに付けると、その後ろの `tool_result` が
  範囲から外れて狭くなるうえ、モデルが返したものに手を入れることになる
  (thinking ブロックは無改変で返す必要があり、書き換えるとそこから先が無効になる)。

`ConvertTo-StableOrder` が**送る直前にキーの並びを固定する。**
PowerShell の Hashtable は並びを約束しておらず、7.x では文字列のハッシュがプロセスごとに
変わるため、同じ payload でも起動のたびに JSON のキー順が変わる ―― そのままでは
**一度も当たらない。** `[ordered]` の並びは書いた順に意味があるので保つ。

### 会話の保存と再開

決まりごとは1つ ―― **過去の発言は書き換えない。足すだけにする。**

| 関数 | 役割 |
|---|---|
| `ConvertTo-SessionJson` | 保存用 JSON。**区切りは外して**保存する (残すと再開のたびに増えて上限を超える) |
| `ConvertFrom-SessionJson` | 読み戻し。ArrayList のまま返す |
| `Get-SessionToolNames` | 会話の中で呼ばれたツール名。再開できるかの判定に使う |
| `Add-ConversationText` | 末尾に利用者側の文面を足す。**宙に浮いたツール呼び出しがあれば先に埋める** |
| `Get-ResumeText` | 続きから再開するときの文面 |
| `Get-HandoffText` | 会話を続けられないときの「前回までの経過」 |

`Add-ConversationText` が扱う末尾の形は3通り。

| 末尾 | すること |
|---|---|
| 空 / `assistant` の最終応答 | `user` の発言を1つ足す |
| `user` (ツールの結果) | その発言の後ろに足す (`user` が2つ続かないように) |
| `assistant` のツール呼び出し | 途中で落ちた跡。**再実行はせず**「実行されたか分からない」と結果を返す |

**`Get-HandoffText` は要約をモデルに書かせない。** DB に残っている事実から組み立てる ――
モデルの書いた経過は自分に都合よく欠ける。#295 の3回目は、実際には PUT していたのに
「GET しか出していない」と書いた。何を叩いて何が返ったかは `task_attempts` が、
何を報告したかは前回の報告が、何が問題だったかは点検の記録が持っている。

## 3. 不変条件

| # | 守っていること | 担保 | 破れたときの症状 |
|---|---|---|---|
| 1 | 同じ内容は同じバイト列になる | `ConvertTo-StableOrder` | キャッシュが一度も当たらず、請求額だけが上がる |
| 2 | 区切りより手前は毎回変わらない | 変わるもの (本文・日時・記憶) は `messages` 側に置く | 同上 |
| 3 | 区切りは1リクエスト4つまで | `Set-CacheBreakpoint` が移す / 保存時に外す | API に弾かれる |
| 4 | モデルが返した `assistant` は無改変で戻す | 応答をそのまま履歴に `Add` | thinking の検証に落ちる。会話が続かなくなる |
| 5 | ツール呼び出しには必ず結果を返す | 中止時・上限時・宙に浮いた分にも `tool_result` を作る | 会話が壊れ、再開できない |
| 6 | 並列で呼ばれたツールの結果は1つの `user` にまとめる | 結果を配列で1回 `Add` | 以後の並列呼び出しが行われなくなる |
| 7 | 拒否 (`stop_reason='refusal'`) を content より先に見る | `Send-ClaudeRequest` | 拒否応答を成果物として扱う |
| 8 | 上限で切れた応答のツールは実行しない | `stop_reason='max_tokens'` で `is_error` を返す | **途中までの入力で書き込む** (ファイルの頭だけで全体を置換) |
| 9 | 第三者の文面はタグの内側、システムの事実は外側 | `InjectionGuard` + 組み立ての分離 | ボード上の文面が指示として効く |
| 10 | 1要素の配列が展開されない | `,@(...)` の先頭カンマ | `system` / `tools` がオブジェクト1個として送られ API に弾かれる |

10 は PowerShell 固有の罠で、このファイルに3か所ある。**配列を返す関数を書いたら必ず確認する。**

## 4. 主要な流れ

### (a) 単発の呼び出し (判定 / 記憶 / 検証)

```
New-BasePayload
  model / max_tokens / system (区切り付き) / tools / tool_choice=強制 /
  output_config.effort / fallbacks='default'
    ↓
Invoke-ClaudeApi → Send-ClaudeRequest
    ↓
content から tool_use を1つ取り出して .input を返す
```

`fallbacks='default'` は、安全分類器が拒否した場合に**同一リクエスト内で代替モデルに回す**設定。
`output_config.effort` は費用の調整。**モデルは落とさず effort で抑える**方針にしてある。

### (b) エージェントループ (`Invoke-ClaudeAgent`)

```
Add-ConversationText (最初の依頼)  → OnSave
for turn = 1..MaxTurns
    Set-CacheBreakpoint (会話の末尾へ移す)
    送信 (context_management 付き。断られたら外して送り直す)
    assistant の応答をそのまま履歴へ            → OnSave
    tool_use が無ければ                         → 終了 (text を返す)
    stop_reason = max_tokens なら               → 実行せず is_error を返して次のターン
    各 tool_use:
        OnProgress で続行を確認 ($false で中止)
        OnTool で実行
    結果を1つの user にまとめて履歴へ            → OnSave
上限に達したら
    ツールを外し (tool_choice='none')、ここまでの報告を書かせて partial で返す
```

**上限で例外にしない**のが要点。最初からやり直させると、その間に外へ出したもの
(コメント・書き込み) だけが増えていく。ツールを取り上げて報告だけ書かせ、
続きは利用者が差し戻したときに**同じ会話から**再開する。

### (c) 作業の依頼の組み立て (`Invoke-ClaudeWork`)

呼び方が3つに分かれる。

| 条件 | 送るもの |
|---|---|
| 会話の続き + 点検の指摘 | 指摘の一覧と「報告は利用者に向けて書き直せ」 |
| 会話の続き + 再開 | `Get-ResumeText` (経過時間・変わった出自・残った指摘・新しい指示) |
| 新規 | カード・名義・`<thread>` (取り直した全文)・台帳・記憶・引き継ぎ・指示 |

取り直しに成功したかどうかで、`<thread>` の直後に付く注意書きが変わる。
成功していれば「**すでに全部読めている。これ以上の取り直しは不要**」と明示する ――
ここが無いと「Gmail を開いてご確認ください」で終わる報告が出る。

## 5. 費用と、効いているかの見方

**キャッシュが効かなくなってもエラーは出ない。請求額が上がるだけ。**
分かるのは応答の `usage` だけなので、足し込んで1行で出す。

```
Reset-ClaudeUsage   … 区切り (通知1巡・カード1枚) の頭で戻す
Add-ClaudeUsage     … Send-ClaudeRequest が毎回足す
Get-ClaudeUsageLine … "API呼び出し 7回 / 入力 120,000 (キャッシュヒット 98,000 ・キャッシング 12,000) / 出力 3,400"
```

**キャッシュヒットが 0 のままキャッシングばかりなら、区切りより手前が毎回変わっている。**
プロンプトの組み立てを疑うこと。

`-Verbose` に頼らないのは、通常の起動 (`Start.ps1`) が3本を別プロセスで立てており、
親に付けた `-Verbose` が子に渡らないため ―― **一番見たい場面で一番出てこない出し方**になる。

### context editing (古いツール結果を消す)

会話が伸びると入力トークンが膨らむので、API 側で古いツール結果を消させる
(`Get-ContextEditing`)。**要約はしない。消すだけ。**
消したあとで要る事実 (何を書き込んだか・利用者の指示・点検の指摘) は、会話ではなく
DB から毎回渡しているので失われない。

消すたびにキャッシュが壊れるので、少しずつではなく**まとめて消す** (`clear_at_least`)。
ベータなので API に断られることがあり、その場合は
`$script:ContextEditingRejected` を立てて**このプロセスでは以後付けない** ――
付けられないことで作業全体を止めるほうが害が大きい。

## 6. 転送 (`Send-ClaudeRequest`)

| 見ているもの | 扱い |
|---|---|
| `stop_reason='refusal'` | 安全分類器の拒否。**HTTP 200 で返る**ので、content を読む前に確認する |
| 429 / 5xx / 例外 | 再試行 (既定2回、2秒・4秒) |
| 4xx (429 以外) | 再試行しない。**エラー本文を読んで投げる** |
| 応答の文字コード | `RawContentStream` から明示的に UTF-8 で読む (5.1 の自動デコードは日本語を壊す) |

エラー本文を読むのは、`400 Bad Request` だけでは何も分からないため。
原因 (残高不足・キー不正・パラメータ誤り) は本文にしか書いていない。

`ConvertTo-Json -Depth 30` は会話の入れ子 (messages → content → tool_use.input → その中身) に
足りる深さ。**足りないと深いところが型名の文字列に化けて、黙って別の入力が送られる。**

## 7. 設定できるもの (`phase2/config/policy.json`)

| キー | 既定 | 何が変わるか |
|---|---|---|
| `llm.model` | `claude-opus-5` | 判定・作業・検証すべて |
| `llm.effort` | `low` | 費用。モデルを落とす代わりにここで抑える |
| `llm.cacheTtl` | `5m` | `1h` は書き込みが2倍の値段。1時間に3回以上通らないと損。`off` で切れる |
| `llm.maxOutputTokens` | 4096 | 単発の呼び出し |
| `llm.maxBodyChars` | 4000 | 通知本文をどこで切るか |
| `worker.maxTurns` | 40 | 1枚のカードでツールを使える回数 |
| `worker.maxOutputTokens` | 16000 | 作業の1応答。thinking と共用なので判定より大きく取る |
| `worker.clearToolResults` / `clearTrigger` / `clearKeep` | true / 80000 / 8 | context editing |

## 9. いま抱えている歪み

- **プロンプトがコードに埋まっている。** `policy.json` で直せるのは方針の一部 (`context`) だけで、
  閉じ方の順序や禁止事項はここを書き換えるしかない。書き換えるとキャッシュも作り直しになる。
- **`Get-WorkSystemPrompt` が 110 行を超え**、禁止事項が積み上がっている。
  それぞれに実際の事故が対応しているので減らしにくいが、読む側の負担は増え続けている。
- **`Invoke-ClaudeWork` の引数が 19 個。** 渡すもの (名義・台帳・記憶・出自・引き継ぎ・指摘) が
  増えるたびに足してきた結果で、呼ぶ側 (`Start-Worker.ps1`) との結合が強い。
- **`$script:ContextEditingRejected` がプロセス全体の状態。** 一度断られると、
  別の条件なら通る場合でも以後付けない。ワーカーは常駐なので、効く時間が長い。
