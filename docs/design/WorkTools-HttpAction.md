# 承認の門 — WorkTools / HttpAction / WritePreview

`phase4/lib/WorkTools.ps1` (約 1,160 行) / `phase4/lib/HttpAction.ps1` (450 行) /
`phase4/lib/WritePreview.ps1` (347 行)

**能力は削らない。削る代わりに、危険なものは実行前に止めて全文を見せる。**
この3ファイルが、モデルの出力と外の世界のあいだに立っている唯一の壁になる。

3つで役割が分かれている。

| | |
|---|---|
| `WorkTools.ps1` | ツールの定義・**危険度の判定**・実行 |
| `HttpAction.ps1` | 汎用 HTTP の実体。**資格情報の注入**と、宛先の禁止 |
| `WritePreview.ps1` | 操作の**種類**の定義、許可の鍵、上書き前の突き合わせと書いたあとの読み直し |

## 1. 役割と境界

| | |
|---|---|
| 担う | 何が危険かの分類 / 承認画面に出す全文の組み立て / 資格情報の注入 / 書き込みの事前確認 / ツールの実行 |
| 担わない | **承認を待つこと自体** (`Start-Worker.ps1` の `Wait-ToolApproval`) / 許可の保存 (`TaskStore`) / 画面 (`Start-Board.ps1`) |

判定と実行が分かれているのが肝心で、`Get-ToolRisk` は**副作用を持たない**。
承認を取るかどうかを決めるのはワーカーで、ここは「危ないかどうか」と
「画面に何を出すか」だけを返す。

依存: `SourceAccess.ps1` / `HttpAction.ps1` / `WritePreview.ps1` / `SecretStore.ps1` / `ApiKey.ps1`。

## 2. ツールの構成 — カードの出口で分けている

| 区分 | ツール | 承認 |
|---|---|---|
| 見る | `open_source` / `fetch_attachment` / `recall` / `read_file` / `list_files` | 不要 (作業フォルダ内・カードに束縛された出自のみ) |
| 作る | `write_file` / `create_email_draft` | 作業フォルダ内 + 安全な拡張子なら不要 |
| 効かせる | `http_request` | **種類 × ホスト**で決まる (後述) |
| 閉じる | `propose_reply` / `send_*` / `add_backlog_comment` / `require_human_step` | 送信系は**必ず**要承認 |
| 調べる | `run_command` | **必ず**要承認 |

`write_file` は既定の出口ではない。完了カードを洗うと、22枚が27個のメモを作業フォルダに
吐いていたが、それらは**何も閉じていなかった**。メモは「他に出口が無かった」ときの
副産物であって成果ではない ―― プロンプト側でもそう書いてある。

**ツール一覧はカードごとに変わる** (`Get-WorkTools`)。

- `propose_reply` は**返信先があるカードにだけ**出す。無いカードに見せると、
  宛先の無い返信を書き始める。
- `send_slack_message` / `send_teams_message` / `send_chatwork_message` /
  `add_backlog_comment` は、**カードの元通知がそのサービスで、かつ接続済み**のときだけ。
- `require_human_step` は**常に見せる。** 呼べるかどうかは別で、証跡が足りなければ
  実行時に差し戻す。一覧から隠す方式も採れるが、一覧はラウンド単位でしか変えられないので、
  同じラウンド内で「調べ尽くしたので諦める」が表現できなくなる。
  **呼ばせたうえで理由とともに突き返すほうが、何が足りないかが伝わる。**

## 3. 危険度の判定 (`Get-ToolRisk`)

返すのは `risky` / `summary` / `detail`、`http_request` ではさらに
`grantKey` / `grantable` / `mustAsk`。

### 分類の基準

**取り返しがつくか**と**作業フォルダの外に影響するか**の2つ。

| ツール | 承認が要らない条件 |
|---|---|
| `write_file` | 作業フォルダ内 **かつ** 安全な拡張子 (`.txt` `.md` `.eml` `.csv` `.json` `.html` `.log` `.yml` `.yaml`) |
| `read_file` / `list_files` | 作業フォルダ内 |
| `http_request` | 読み取り (GET/HEAD/OPTIONS) **かつ** 認証が付く既知のホスト |
| `open_source` / `fetch_attachment` / `recall` / `record_finding` / `require_human_step` | 常に不要 (外に出ない・カードに束縛されている) |

`Test-InWorkspace` は**単なる前方一致ではない。**

```
C:\...\output\task-0001          作業フォルダ
C:\...\output\task-0001-x\a.md   前方一致は通るが、別のフォルダ
```

承認の要否がこの判定で決まるので、区切り文字まで見て隣を弾く。

### 承認画面に何を出すか

**宛先と名義は、モデルの入力ではなくワーカーが束縛したものを出す。**
「モデルが言った宛先」を出しては壁にならない。

```
投稿先: #general (元の通知のチャンネルから束縛)
名義:   あなた (me@example.com) ← 繋いだアカウントから決まる。Bot ではない
形式:   元のスレッドへの返信として

--- 本文 ---
(全文。切らない)

※投稿すると取り消せません。あなたの発言として相手に届きます。
```

書き込みの本文は**切らない。** 取り消せない操作の唯一の事前確認だから。
符号化するフィールド (`encode`) は**平文のまま見せる** ―― base64 のままでは、
人が読んで「中身が 1/400 になる」ことに気付けない (#295)。

## 4. http_request — 束縛を URL から資格情報へ移す

### なぜそうしたか

原則は「宛先はモデルに決めさせない」だった。送信ツールはカードの元通知から投稿先を
束縛していて、モデルは宛先を指定できない。**だが API を叩く操作にその形は使えない。**
叩き先は事前に列挙できないし、用途ごとに専用ツールを生やすと、カレンダーの出欠、
GitHub の招待、と際限なく増える割に、少し形の違う依頼が来たとたん何も出来なくなる。

そこで**束縛する対象を変えた。** URL はモデルが自由に決めてよい。代わりに
**資格情報はモデルに一切渡さない。**

- モデルはトークンを見られないので、どこかへ書き出すことができない
- Google のトークンは `googleapis.com` にしか付かない。**未知のホストには何も付かない**ので、
  資格情報を持ち出す経路が原理的に存在しない
- 承認画面には実際に飛ぶリクエストが出る。認証行は名前だけ (`GitHub トークン`) を出す

### ホストと資格情報の対応 (`$script:CredentialHosts`)

| サービス | ホスト | 取り方 |
|---|---|---|
| github | `api.github.com` ほか | 保管庫 (`github.token`)、`Bearer` |
| google | `googleapis.com` | `Get-GmailAccessToken` (動的) |
| slack | `slack.com` | `Get-SlackToken` (動的) |
| microsoft | `graph.microsoft.com` | `Get-GraphAccessToken` (動的)。Outlook と Teams は同じ入口 |
| chatwork | `api.chatwork.com` | 保管庫。`X-ChatWorkToken` ヘッダ |
| anthropic | `api.anthropic.com` | 通常キー。**`/v1/organizations` だけ管理 API キー** |

2つの決まりがある。

- **クエリ文字列に載せる方式のサービスはここに書かない。** URL に載った時点で
  承認画面と作業ログに鍵が残り、「トークンを URL に入れない」という約束が崩れる
  (Backlog がこれに当たるので、専用のコネクタ経由でだけ叩く)。
- **`path` を書いた項目は狭いほうを上に置く。** 先に書いたものが勝つ。
  同じホストでも道によって鍵が変わる API (Claude の組織向けの口) のため。

### 実行時に通す関門 (`Invoke-HttpAction`)

```
1. Test-BoundOnlyEndpoint   人に届く送信の口は、汎用ツールからは叩けない
2. Test-SecretLeak          保管中の鍵が URL / 本文に混ざっていたら送らずに中止
3. 認証ヘッダを捨てる        モデルが書いた Authorization / そのホストの認証ヘッダは削除
4. 資格情報を注入           ホストから決まるものだけ。failed なら送らずに理由を返す
5. 送信 → 応答を返す         4xx/5xx も本文ごと返す (原因は本文にしか書いていない)
```

1 は**塞ぎ過ぎる側に倒している。** メソッド未指定なら「どのメソッドか分からない」と
みなして、メソッド指定の項目にも当てる。ここが壁だから。

2 が必要なのは、モデルが資格情報を渡されなくても、**作業中に読んだファイルや
コマンド出力からトークンらしき文字列を拾うことがある**ため。
秘密ではない識別子 (クライアント ID、テナント ID、スペース名) は見ない ――
URL に載って当たり前の値で、ここで止めると正しい呼び出しが通らなくなる。

3 は「取れなかったときだけ素通り」にしない。未設定のあいだはモデルが書いた
`X-ChatWorkToken` がそのまま飛ぶことになり、**カードに載った第三者の文面から
トークンらしき文字列を拾って付ける**筋道が残る。

4 の `Get-CredentialStatus` は**「未設定」と「設定済みだが取得に失敗」を分ける。**
利用者のやることが違うから。以前は失敗を握り潰して「無い」扱いにしていたため、
認証なしで飛んで 401 になり、ワーカーには「トークンが設定されていません」と伝わっていた ――
実際は Google 側で許可が取り消されていた、という失敗が名指しされないまま、
設定済みの画面と食い違う報告が出ていた。

## 5. 許可の単位と、上書きの事前確認

### 操作の種類 (`Get-HttpOpKind`)

| 種類 | メソッド | 性質 |
|---|---|---|
| `read` | GET / HEAD / OPTIONS | 読むだけ |
| `add` | POST | 相手に新しいものを足す。取り消しても害が小さいことが多い |
| `change` | PUT / PATCH / DELETE | **いまあるものを上書きする・消す。送らなかった部分は消える** |

許可の鍵は `http_request:{種類}:{ホスト}` (`Get-GrantKey`)。
以前はツール名で束ねていたので、**GET を通すために押した「今後すべて許可」が
GitHub への PUT まで無承認にしていた** (#295)。

### 上書きの前に何が起きるかを見せる (`Get-WritePreview`)

`change` のときだけ、同じ URL を GET していまの状態を取り、送る本文と
**フィールドごとに**突き合わせる。

| `level` | 意味 |
|---|---|
| `compared` | フィールドごとに突き合わせた |
| `new` | GET が 404。新しく作る操作 |
| `shown` | 読めたが形が違って突き合わせられない |
| `unavailable` | 読めなかった |

比べるのは**両方にあるフィールドだけ。** GET の応答には送らないメタ情報
(sha・url・更新日時) が並ぶのが普通で、それを「消える」と数えると毎回騒ぐことになる。
**base64 の値はデコードしてから比べる** (`Get-ComparableValue`)。

元が 200 字 (バイト) 以上あって半分未満に減るフィールドがあれば `largeLoss` が立ち、**許可があっても YOLO でも止まる**
(`mustAsk`)。さらにワーカー側で、`confirm_large_change` が無ければ
**承認に回す前に差分をモデルへ返す** ―― モデル自身が取り違えに気付ける最後の機会で、
#295 の PUT (10,361 → 24 バイト) はここで止まる。

突き合わせられなかった `change` は `grantable = $false` にする。
**影響を事前に確かめられない上書きは束ねない。**

### base64 はモデルに手で書かせない (`ConvertTo-EncodedBody`)

ファイルを丸ごと送る API (GitHub の contents、Gmail の raw) は値を base64 で求める。
手で書かせると、長さの分だけ出力を食い、1文字でも誤れば中身が壊れる
(1万字のファイルは base64 で 1.4 万字になり、4096 トークンの上限では最初から書き切れない)。
**モデルは平文で書き、`encode` でフィールド名だけを指定する。**
手書きの base64 を見つけたら (`Find-HandWrittenBase64`) 送らずに差し戻す。

### 書いたあとに読み直す (`Get-ReadbackCheck`)

PUT / PATCH が成功したら、同じ URL をもう一度 GET して送った値と一致しているかを返す。
**書いたつもりのものと実際に入ったものの食い違いに、その場で気付けるようにする。**

## 6. 人間送りの門 (`Test-HumanStepAllowed`)

`require_human_step` は**正式な出口**であって失敗ではない。ただし安易には使えない。

理由は自由記述ではなく、この5つから選ばせる。

| blocker | 意味 | 扱い |
|---|---|---|
| `credential_missing` | 権限・資格情報が足りない | カードを閉じず、**設定カードに変換** |
| `physical_presence` | 本人の身体が要る (生体認証・本人確認リンク) | そのまま出口 |
| `payment_or_legal` | 支払い・契約・本人の意思決定 | そのまま出口 |
| `no_api` | 相手側に操作する手段が無い | **試した証跡が要る** |
| `beyond_tools` | 手持ちの道具では正しくできない (引き渡す) | そのまま出口 |

**差し戻す条件**:

| 条件 | 差し戻す理由 |
|---|---|
| `open_source` を呼んでいない | カードの本文は途中までのことがある。全部読んでから判断させる |
| `credential_missing` なのに `http_request` の記録が無い | 権限不足は**叩いて断られた記録**が根拠。推測で諦めさせない |
| `no_api` なのに `http_request` の記録が無い | 同上。調べずに宣言させない |

`physical_presence` / `payment_or_legal` / `beyond_tools` は証跡を求めない ――
いくら叩いても解決しないし、**`beyond_tools` で試行を求めると、試すこと自体
(HTTP でファイル編集を組み立てる) が壊す原因になる** (#295)。

`Get-HumanStepHeadline` が報告の**先頭**に1手を置く。経過の下に埋めると読まれない。
証跡 (何を試して何が返ったか) を必ず一緒に出すのは、「サボったのでは」という疑いを
晴らすために利用者が結局元通知を見に行く、という往復を無くすため。

## 7. 不変条件

| # | 守っていること | 担保 | 破れたときの症状 |
|---|---|---|---|
| 1 | モデルはトークンを受け取らない | 注入は `Invoke-HttpAction` の中だけ | 鍵が会話とログに載り、外へ出る経路ができる |
| 2 | 認証はホストから決まる | `Get-HostCredentialSpec` のサフィックス一致 | 未知のホストへ鍵が付く |
| 3 | モデルの認証ヘッダは必ず捨てる | 資格情報が取れたかに関わらず削除 | 第三者の文面から拾った値がそのまま飛ぶ |
| 4 | 人に届く送信は汎用ツールから叩けない | `Test-BoundOnlyEndpoint` | 宛先の束縛が丸ごと素通しになる |
| 5 | 承認画面の宛先と名義はワーカーが束縛したもの | `Get-ToolRisk` の引数 | 画面が壁にならない |
| 6 | 書き込みの本文は切らずに出す | `Get-ToolRisk` の `http_request` 分岐 | 何を書くか分からないまま承認される |
| 7 | 許可は「種類 × ホスト」で束ねる | `Get-GrantKey` | GET の許可が PUT を通す (#295) |
| 8 | 確かめられない上書きは束ねない | `grantable = $false` | 影響不明の書き込みが無承認で通る |
| 9 | 大きく減る書き込みは許可でも YOLO でも止まる | `mustAsk` | ファイルが1行に置き換わる (#295) |
| 10 | 作業フォルダの判定は区切り文字まで見る | `Test-InWorkspace` | 隣のフォルダが「中」と判定される |
| 11 | 人間送りは証跡が無ければ差し戻す | `Test-HumanStepAllowed` | 「ご自身でリンクから」で閉じるカードが並ぶ |

## 8. 実行の全体の流れ (ワーカー側から見たとき)

```
モデルが tool_use を返す
  │
  ├ http_request なら
  │    ConvertTo-EncodedBody      平文 → base64 (指定されたフィールドだけ)
  │    Find-HandWrittenBase64     手書きの base64 は送らず差し戻す
  │    change なら Get-CurrentState → Get-WritePreview
  │        largeLoss かつ confirm_large_change 無し → 実行せず差分を返す
  │
  ├ Get-ToolRisk                  危険度・画面の全文・許可の鍵
  │    risky なら Wait-ToolApproval
  │        mustAsk          → 必ず画面に出す (YOLO も許可も効かない)
  │        YOLO             → 通す
  │        grantable + 許可済み → 通す
  │        それ以外          → tool_requests に積んで待つ (既定のタイムアウトあり)
  │        approved 以外     → 実行せず、理由をモデルに返す (拒否も証跡に残す)
  │
  ├ Invoke-WorkTool               実行。宛先はすべてワーカーが束縛して渡す
  │
  ├ PUT/PATCH なら Get-ReadbackCheck   読み直して送った値と突き合わせ
  └ Add-TaskAttempt               何を叩いて何が返ったか。書き込みは本文と突き合わせも全文
```

**拒否は例外にせずモデルに返す。** 理由が伝われば別の手を考えられる。
「試したが利用者が止めた」と「そもそも試していない」は別物なので、拒否も証跡に残す。

## 10. いま抱えている歪み

- **`Get-ToolRisk` が 240 行の `switch`。** ツールを足すたびに伸びる。
  分岐ごとに画面の文面が直書きされているので、送信系で同じ形を5回繰り返している。
- **ツールごとの束縛パラメータが `Invoke-WorkTool` の引数に並んでいる** (Gmail / Slack /
  Outlook / Teams / Chatwork / Backlog で 10 個)。サービスを足すたびに増える。
- **`$script:CredentialHosts` の順序に意味がある。** `path` 付きを上に置く決まりが
  コメントにしか書かれておらず、順序を崩すと Claude の管理 API が通らなくなる。
- **`Get-CurrentState` は `change` のたびに GET を1回増やす。** 安全のための費用として
  受け入れているが、レート制限のあるホストでは効く。
- **`Test-SecretLeak` は完全一致でしか見ない。** 分割して埋め込まれた鍵は素通りする。
  ここは「うっかり」を止める仕掛けであって、敵対的な回避には耐えない。
