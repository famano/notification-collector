# Board — カンバン (ローカル Web サーバと画面)

`phase3/Start-Board.ps1` (約 1,620 行) / `phase3/lib/RequestGuard.ps1` (55 行) /
`phase3/lib/SetupFlow.ps1` (74 行) / `phase3/wwwroot/index.html` (単一ファイル)

.NET の `HttpListener` で 127.0.0.1 に立てる。**追加インストールも管理者権限も要らない。**
画面は素の HTML / CSS / JavaScript が1ファイル ―― ビルドを挟むと、
配った先で直せなくなる。

このシステムの主張が一番はっきり出るのがここで、**利用者がする操作はすべてこの画面で閉じる**
(承認・差し戻し・送信・設定・方針の調整・記憶の削除)。

---

## 1. 役割と境界

| | |
|---|---|
| 担う | HTTP の受け口と JSON API / 静的ファイル / **宛先の決定** / 出口 (送る・完了・差し戻す) / 設定と OAuth の戻り先 / 画面 |
| 担わない | 判定 (`Invoke-Triage`) / 作業 (`Start-Worker`) / 承認するかどうかの判断 (利用者) |

依存は広い ―― `TaskStore` / `Policy` / `Memory` / `Dossier` / `Delegation` /
phase5 の全コネクタ / `ServiceSetup`。
ただし**コネクタの読み込みは任意扱い**で、失敗してもボードは起動する
(`$script:Connectors = $false` になり、送信と設定の口が出ないだけ)。

---

## 2. 通信の入口と、通すかどうか (`RequestGuard.ps1`)

判定を**別ファイルに切り出してある。** ここはボードの中で唯一、
**壊れても画面に何も出ない場所**だから ―― 緩めた瞬間から「普通に動いているように見えるが、
外から操作できる」状態になり、気付く手がかりが無い。
要求ループの中に直接書くと、ボードを起動しないと確かめられず、結局確かめられない。

| 関数 | 何を見るか | 何を防ぐか |
|---|---|---|
| `Test-AllowedHost` | `Host` が `localhost` / `127.0.0.1` か | **DNS リバインディング** (127.0.0.1 に解決される名前で同一オリジンを装う) |
| `Test-AllowedOrigin` | 状態を変える要求の `Origin` が**自分自身のポート**か | **CSRF** (応答は読めなくても、起こす方は成立する) |

`Test-AllowedOrigin` が**ポートまで見る**のが要点。以前は localhost ならポートを問わず
通していたので、同じ PC の別のローカルサーバ (開発サーバ、他のアプリのローカル UI) が
出したページから削除や送信を起こせた。

**防げないもの** ―― ここを誤解しないこと:

> **同じ PC で動くネイティブなプロセスは素通りする。** `Origin` はブラウザが付けるヘッダで、
> curl 相当のものは付けないし詐称もできる。この層は**ブラウザ経由の攻撃だけ**を見ている。
> ローカルのプロセスに対しては「**資格情報そのものを API から返さない**」ことで被害を抑えている。

## 3. 宛先はサーバが決める (`Get-TaskOutlet`)

カードは「何をもって完了とするか」で2種類しかない。

| | |
|---|---|
| 送る | 返信・投稿で終わる。**宛先がカードの元イベントから束縛できる** |
| 実施 | 自分が手を動かして終わる。送り先が無い (PC の内部通知など) |

どちらも最後に残るのは1つのテキストで、**違うのは押すボタンだけ。**

**宛先はリクエストから受け取らない。** 受け取れる作りにすると、
ボードに流し込まれた第三者の文面から宛先を差し替える道ができる。

| 由来 | 出口 | 宛先の取り出し元 |
|---|---|---|
| Gmail / Outlook | `{差出人} へメールを返信` | `raw_json.from`。件名に `Re:` を足す |
| Slack | `{チャンネル名} のスレッドへ投稿` | 通知の `slack://` リンク |
| Teams | `{チャット名} のチャットへ投稿` | 通知の `msteams://` リンク |
| Chatwork | `{部屋名} へ投稿` | リンク |
| Backlog | `課題 {キー} へコメント` | `raw_json.issueKey` またはリンク |

宛先を引くのに外を叩く (チャンネル名・部屋名) ので、**どのアカウントで叩くかを
先に固定する** (`Use-EventAccount`)。束縛しないと、繋いだうちのどれかで引くことになり、
読めなければ宛先が消え、読めてしまえば**別のワークスペースの名前が付く。**

引けなかった場合は例外にせず「実施」として扱う ―― 投稿先が分からないだけで、
カード自体は閉じられる。

## 4. カードを閉じる出口

レビューで実際に読むのは**ワーカーの報告**で、読んだあとにすることは3つしかない。

| 出口 | API | すること |
|---|---|---|
| 承認して終了 | `/api/tasks/{id}/approve` | 記録を書き写させず、**承認した事実だけ**を残して `done` |
| 自分で対応して終了 | `/api/tasks/{id}/done` | 書いた内容を `user_record` に。**空でもよい** |
| 差し戻す (+指示) | `/api/tasks/{id}/comment` | 指示を積んで `todo` へ。中止フラグも解く |
| 送る | `/api/tasks/{id}/send` | 下記 |

**「保存しても何も起きない欄」は置かない。** どの道でも、書いた内容がカードを閉じる
操作に直結する。記録を `user_record` に入れるのは、`user_edited` が**送る文面の箱**だから ――
そこに書くと「送らずに完了」した記録が送信欄に出てしまう。

### 送信の口だけ条件を厚くする

送ると取り消せないので、ここだけ4つ重ねる。

```
1. 宛先はサーバが元イベントから決める     リクエストの宛先は受け取らない
2. confirm が無いと送らない               UI の確認ダイアログを通った印
3. 送る文面を先に user_edited へ保存      送ったものと画面に残るものを一致させる
4. version 照合                          画面が古いまま押したら 409
```

さらに、**送る前にアカウントを自分で固定し直す。** `Get-TaskOutlet` の中でも束縛しているが、
送信は取り消せないので、**呼ぶ順を変えた誰かに壊させない**ようにする。

**送信は終わりとは限らない。**「承知しました、対応します」と返してから実際の作業が
始まる用件があり、そこで完了に落とすとカードが行方不明になる。
`finish=false` なら、送ったうえで `todo` に戻して続きをワーカーに拾わせる。

## 5. 画面から直せるもの

「直せる場所がテキストエディタだと、たいてい直されない」というのがこの節の全部。

| 対象 | API | なぜ画面に要るか |
|---|---|---|
| 方針 (`ignore`) | `/api/policy/ignore` | 「この通知は今後要らない」と分かるのはカードを見た瞬間 |
| 背景情報 (`context`) | `/api/policy/context` | 判定の精度に直結する |
| 覚えたこと | `/api/memory` (GET/DELETE) | **間違って覚えたものを消せる口**が無いと、一度の言い間違いが延々と残る |
| 自動承認 (YOLO) | `/api/settings/yolo` | |
| まとめて許可の取り消し | `/api/grants/{id}` (DELETE) | |
| 接続・アカウント | `/api/setup/...` | 設定カードの出口 (次節) |

**ふるいの条件はサーバがカードの元イベントから取る。**
画面から任意の文字列を受け取れる作りにすると、ボードに載った第三者の文面から
「全部無視」に近い条件を仕込む道ができる。

## 6. 設定カードの出口 (`SetupFlow.ps1`)

資格情報が足りなくて止まったカードには設定カードが立つ (`TaskStore.New-SetupTask`)。
**そのカードを開いて、保存・疎通確認・止まっていたカードの再開までをその場で終わらせる。**

```
/api/setup            GET   設定済みか、どのアカウントとして繋がったか (値は返さない)
/api/setup/{svc}      POST  トークンを貼る形
/api/setup/{svc}/authorize + /oauth/{svc}/callback   同意画面を通る形 (Google / Slack)
/api/setup/{svc}/devicecode + /poll                  デバイスコード形 (Microsoft)
/api/setup/{svc}/accounts ...                        アカウントの枠の出し入れ
/api/setup/{svc}/attention                           「使う」/「警告しない」
```

保存に成功したら `Get-TasksWaitingForSetup` → `Resume-Task` で、
**待っていたカードをまとめて `todo` に戻す。**
設定カードの狙いは「1枚直せば同種がまとめて通る」なので、
1枚ずつ手で戻すのでは半分しか叶わない。

**API は値を返さない。** 返すのは「設定済みか」と「どのアカウントとして繋がったか」だけ ――
同じ PC のネイティブなプロセスを弾けない以上、ここが最後の線になる。

## 7. 画面 (`wwwroot/index.html`)

### 更新はポーリング + 版番号

```
1.5 秒ごとに /api/rev  →  変わっていたら /api/board を取り直す
```

`Get-BoardRevision` が件数と最終更新をまとめた安い1行を返すので、
**変わっていないときは何も取らない。** ワーカーのハートビートは版に含めない
(5秒ごとに版が変わってボード全体の再取得が走り続ける)。

### `innerHTML` を使わない

**報告には第三者の文面が引用として混ざる。**
だから描画はすべて `createElement` + `textContent` で組む。

その上で、報告は**書式のまま**描く ―― カードを開いて実際に読むのは報告だけなのに、
折りたたみの中に記号のまま置いていたので、長いものほど読めなかった。
いまは先頭に畳まずに出し、見出し・箇条書き・表・引用を自前の描画関数
(`mdInline` / `mdList` / `mdCells` …) で組む。**通すのは自分が知っている記法だけで、
生の HTML は素通ししない。**

### 状態の保ち方

| 保つもの | なぜ |
|---|---|
| 折りたたみの開閉 (`openSections`) | カードを開き直すたびに畳まれると読み進められない |
| 選んだ出口 (`exitTab`) | 更新のたびに既定へ戻ると、**書きかけの欄ごと切り替わる** |

## 8. 起動時の作法

**ポートが埋まっていたら隣を試す** (既定 8787 から +9 まで)。
そこで諦めると監視役が延々と起動し直すだけになり、画面は最後まで開かない ――
配った先では「アイコンを押しても何も起きない」としか見えず、直しようがない。

実際に開いたポートは `settings.board.url` に残す。監視役 (`Start.ps1`) がこれを読んで
本当の URL を出す ―― **案内した番号が違うと、「開かない」と言われたときに
見に行く先まで間違える。** OAuth の戻り先も実際に開いたポートで組み立てる。

### 要求ごとの後始末

```
finally {
    レスポンスを閉じる
    Reset-AccountSelection      ← カード1枚のために切り替えたアカウントを持ち越さない
}
```

持ち越すと、**無関係な要求がそのカードの相手の資格情報で動く。**

## 9. 不変条件

| # | 守っていること | 担保 | 破れたときの症状 |
|---|---|---|---|
| 1 | 外から叩けない | `Test-AllowedHost` / `Test-AllowedOrigin` | 見た目は正常なまま、外から操作される |
| 2 | `Origin` はポートまで一致させる | `Test-AllowedOrigin` | 同じ PC の別ローカルサーバから削除・送信が通る |
| 3 | 宛先はリクエストから受け取らない | `Get-TaskOutlet` がイベントから決める | ボード上の文面で宛先を差し替えられる |
| 4 | ふるいの条件もリクエストから受け取らない | サーバがイベントから取る | 「全部無視」を仕込まれる |
| 5 | 資格情報は API から返さない | `/api/setup` は状態だけ | ローカルプロセスに鍵が渡る |
| 6 | 送信は confirm + version + 事前保存 | 送信ルート | 画面が古いまま二重送信・文面の食い違い |
| 7 | アカウントの束縛を要求間で持ち越さない | `Reset-AccountSelection` | 無関係な要求が他人の資格情報で動く |
| 8 | 画面は `innerHTML` を使わない | `createElement` + `textContent` | 通知本文から DOM を注入される |
| 9 | 作業フォルダのパスはサーバが決める | DB の記録から | 任意のフォルダを開かせられる |
| 10 | 実際に開いたポートを記録する | `settings.board.url` | 案内する URL がずれる |

## 11. いま抱えている歪み

- **`Invoke-Route` が 900 行あまりの `if` の連なり。** ルーティング表を持たず、
  上から順に `$path -match` している。ルートを足すのは簡単だが、
  全体像は読まないと分からない。
- **`Start-Board.ps1` が API・出口の判断・コネクタの呼び出しを兼ねている。**
  送信の実体はコネクタにあるが、どのコネクタを呼ぶかの分岐はここにあり、
  `Start-Worker.ps1` の同じ分岐と二重になっている。
- **画面が1ファイル 2,600 行あまり。** ビルドを挟まない方針の代償で、
  配った先で直せる利点と引き換えになっている。
- **ポーリングが 1.5 秒固定。** カードが増えると `/api/board` の応答も伸びるが、
  いまは版番号で取りに行く回数を抑えているだけ。
