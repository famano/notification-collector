# Worker — カード1枚を閉じるまで

`phase4/Start-Worker.ps1` (約 1,040 行) / `phase4/lib/WorkSession.ps1` (105 行)

`todo` のカードを1枚ずつ拾い、**実際に用事を終わらせて** `review` に置く常駐プロセス。
モデルを呼ぶのは `ClaudeClient`、ツールの中身は `WorkTools` にあるので、
ここにあるのは**その間を取り持つ手続き**と、**守らせたいことを構造で担保する仕掛け**。

---

## 1. 役割と境界

| | |
|---|---|
| 担う | カードの取得とリース / 出自の取り直し / 宛先と名義の束縛 / 承認を待つこと / 会話の再開の判断 / 自己検証と直し / 報告の組み立て / 記憶の取り込み / 失敗の棚上げ |
| 担わない | モデルとの通信 (`ClaudeClient`) / 危険度の判定 (`WorkTools`) / 資格情報の注入 (`HttpAction`) / 画面 (`Start-Board`) |

このファイルの通しての方針は1つ ――
**「モデルに指示して守らせる」のではなく、構造で守る。**

| 守らせたいこと | 指示でやろうとして失敗した | いまの担保 |
|---|---|---|
| 本文を全部読んでから判断する | 「まず `open_source` を呼べ」 | **ワーカーが先に取り直して渡す** |
| 投稿先を取り違えない | — | カードの元通知から束縛し、ツールには渡さない |
| 他人の名義で書かない | スレッド全文だけ渡していた | 繋いだアカウントから名義を作って渡す |
| 前回何をしたか踏まえる | — | 会話を残し、続きから再開する |

## 2. カード1枚の流れ (`Invoke-WorkItem`)

```
Get-NextWorkItem            todo か、リース切れの doing を1枚。設定カードは拾わない
  │
  ├ 未読コメントを読む        既読にするのは「ここで読んだ分まで」(watermark)
  ├ アカウントを固定          Use-EventAccount。以降の経路は意識しなくてよい
  ├ 名義を作る                New-Viewer (本人は誰か)
  ├ 投稿先を束縛              Slack / Teams / Chatwork / Backlog / Gmail / Outlook
  ├ 前回の human_step を消す   それは「前回の」結論
  │
  ├ 出自を取り直す            Get-SourceContext → 本文・識別子・添付・リンク
  │     立場 (宛先 / Cc) はここで名義に足される
  │     取り直しも証跡に残す ← 残さないと人間送りの門が「まだ読んでいない」と誤判定する
  │
  ├ 会話の計画                Get-SessionPlan → new / resume / handoff
  │
  └ while (直しのループ)
        Invoke-ClaudeWork     ツールの実行は onTool、進捗と中止は onProgress
        partial なら           点検せずに利用者へ渡す
        自己検証               別の会話で点検 (Invoke-ClaudeVerify)
        送信済みなら           直さない。high があれば alert を立てて赤く出す
        MaxRepairs を超えたら   人間の確認へ
        ↓
     報告を組み立てて agent_output と task_comments(kind='report') に
     作業中に届いた指示があれば todo に戻す。なければ review へ
```

### 未読コメントの watermark

作業の最初に読んだ分だけを既読にする。**全部を既読にすると、作業中に届いた指示が
一度も読まれないまま消える。** 終わったあとにもう一度見て、未読があれば
`review` ではなく `todo` に戻す ―― 指示を書くのは「やり直して」の意思表示だから。

カンバン側で `doing` のカードを動かさないのは、**中止要求と区別が付かなくなる**ため。
だから実行中に届いた指示は、ここで拾う役割になっている。

### 出自の取り直し

**モデルに頼まず、ワーカーが先にやる。**「まず `open_source` を呼べ」という指示は
守られなかった ―― カードの見出しだけで十分だと判断して `write_file` に直行し、
本文の後半を読まないまま報告が出る。**先に取ってから渡せば「読んでいない」という
状態が存在しなくなる。**

渡す形は4つに分かれている。

```
識別子 (http_request で使えます):  … スレッド ID、メッセージ ID
添付 (fetch_attachment で読めます): … id / 名前 / MIME / サイズ
本文中のリンク:
本文:
```

### 宛先と名義の束縛

| 由来 | 束縛するもの | 取り出し元 |
|---|---|---|
| Gmail | `threadId` / `messageId` | `raw_json` |
| Outlook | メッセージ ID | `raw_json` (Graph の `createReply` が件名も会話も引き継ぐので1つでよい) |
| Slack | チャンネル / スレッド ts / チャンネル名 | 通知の `slack://` リンク |
| Teams | チャット ID / チャット名 | 通知の `msteams://` リンク |
| Chatwork | 部屋 ID / メッセージ ID / 相手のアカウント ID | リンクと `raw_json` |
| Backlog | 課題キー | `raw_json` またはリンク |

**束縛に失敗しても作業は続ける。** そのサービスの投稿ツールが一覧に出ないだけ。

## 3. 承認 (`Wait-ToolApproval`)

危険度の判定は `WorkTools` が返すので、ここは**待ち方**だけを持つ。

```
mustAsk (大きく減る上書き)   → YOLO も許可も効かない。必ず画面に出す
Test-YoloMode               → 通す
grantable かつ許可済み        → 通す
それ以外                     → tool_requests に積んで、2秒ごとに見ながら待つ
```

待っているあいだも `worker_state` を更新し続ける。**止めると画面上は「応答なし」に見える。**

`ApprovalTimeoutSec` (既定 600 秒) を過ぎたら `expired`。
**拒否・期限切れ・中止はいずれも例外にせず、理由をモデルに返す** ――
理由が伝われば別の手を考えられる。そして**拒否も証跡 (`task_attempts`) に残す**:
「試したが利用者が止めた」と「そもそも試していない」は別物だから。

## 4. 会話をどう始めるか (`Get-SessionPlan`)

ワーカーは以前、やり直しのたびに会話を捨てていた。差し戻すと最初から調べ直し、
**自分が前回何をしたか (何を書き込んだか) を知らないまま作業する。**
#295 では「テストファイルを空にしたのはきみか」と聞かれて「GET しか出していない」と答えた。

| mode | 条件 | 渡すもの |
|---|---|---|
| `resume` | 会話が残っていて、そのまま使える | `Get-ResumeText` (経過時間・変わった出自・残った指摘・新しい指示) |
| `handoff` | 会話を使えない | `Get-HandoffText` (試したこと・前回の報告・残った指摘) |
| `new` | 会話も履歴も無い | 通常の依頼 |

**`resume` にできない条件** (どれも会話を捨てて記録から引き継ぐ):

- **同じ件の新しい発生** (`occurrence` が違う)。次の CI の失敗は別の出来事
- 会話が長すぎる (`MaxSessionChars`、既定 200 万字)
- **前回呼んだツールが今の一覧に無い。** 宙に浮いた呼び出しを抱えた会話は API に弾かれる
  (コードの更新、連携の解除で起きる)
- 会話を保存する前からあるカード

出自の指紋 (`source_hash`) が前回と違えば、**変わった全文を差分として渡す** ――
前回から時間が経っており、そのあいだに外の状態は変わりうる。#295 では、
ワーカーが壊したファイルを利用者が手で直していた。

## 5. カードの閉じ方と、その扱い

モデルが呼ぶツールによって、ワーカー側の後始末が変わる。

| ツール | ワーカーがすること |
|---|---|
| `propose_reply` | `draft_text` に入れる。**`user_edited` は踏まない** (利用者が手を入れた内容は消えない) |
| `record_finding` | `dossier` に残す。カードをまたいで効く事実だけ |
| `send_*` | `sentItems` に控える。**送信はファイルに残らない**ので、検証と報告のために別に持つ |
| `require_human_step` | 証跡で妥当性を判定。`blocker` ごとに扱いが変わる (下記) |

### `credential_missing` は投げ返さない

完了カードを洗うと、29枚中8枚が「権限が無くて進めない」で止まっていた。
これは1枚ずつ人間に投げ返す問題ではなく、**一度設定すれば同種がまとめて通る。**

```
require_human_step(blocker='credential_missing')
  ├ New-SetupTask         サービス単位で1枚。鍵はモデルの文章ではなく
  │                       失敗したリクエストのホストから決める (setup:github)
  ├ dossier(svc:github)   権限の不足は件を越えて効くのでサービス単位でも残す
  └ 元のカードは shape='blocked'
```

**元のカードを `setup` にしてはいけない。** 設定カードはワーカーの取得対象から外れる
仕様なので、`setup` を付けると資格情報を入れたあとも二度と再開されなくなる。

### `human_step` は DB を唯一の出どころにする

ツールの実行はクロージャの中で起きる。`GetNewClosure()` は変数を**複製する**ので、
クロージャの中で立てた変数は外の関数に届かない。そのため
「報告の先頭に出るはずの【あなたの操作が必要です】が一度も出ない」
「自己検証に `human_step` が渡らない」が起きていた (カード自体には出るので気付きにくい)。
いまは**クロージャが DB に書き、呼び出し側が読み直す** (`Get-TaskHumanStep`)。

## 6. 自己検証と、直しに回さない条件

作成時とは**別の会話**で点検する (`Invoke-ClaudeVerify`)。渡すのは
成果物・報告・利用者の指示・送信したもの・**試したことの記録**・`human_step`・名義。

点検が見るのは、依頼が満たされているか、途中で終わっていないか、名義を取り違えていないか、
そして**手を尽くさずに投げ返していないか / やりすぎていないか**。
「権限が無い」は**実際に叩いて断られた記録が無ければ high** になる。

**直しに回さない条件**:

| 条件 | なぜ |
|---|---|
| `partial` (回数の上限で止めた) | 途中の報告は「終わっていない」と言われるだけで、直すとまた上限まで走る |
| **送信済み** (`sentItems` がある) | 送ったものは取り消せない。もう一度走らせると二通目が出かねない |
| `MaxRepairs` (既定1回) を超えた | 人間の確認へ |

送信済みで high の指摘が出た場合は、**`tasks.alert` を立てて赤く出し続ける。**
#295 では点検が「ファイルを1行にして壊した」と正しく見つけていたのに、
普段どおりのレビュー待ちに置かれ、利用者はリポジトリがおかしくなってから気付いた。

## 7. 報告の組み立て

順序に意味がある。**上から読んで分かる形**にする。

```
【あなたの操作が必要です】/【…引き渡します】   ← これが結論なので先頭
  ここに至るまでに試したこと (証跡)
---
【途中で止まっています】(partial のとき)
---
モデルが書いた報告
作成したファイル:
送信済み (n 件):
```

**自己検証の結果は報告に書かない。** 以前は末尾に「[自己検証: 問題なし]」を付けていたが、
利用者が読んでも判断が変わらない (問題なしなら読み飛ばし、要確認なら指摘そのものが要る)。
結果は作業ログに、解消しなかった指摘は `task_comments(kind='verify')` に残して
次の作業に渡す。

報告は `agent_output` (最新1件) と `task_comments(kind='report')` の**両方**に入れる。
前者だけだと、差し戻すたびに前回の報告が読めなくなる。

## 8. 主ループと失敗の扱い

```
while (true)
    Get-NextWorkItem
      │ null なら → Update-MemoryFromClosedCards (1枚)、idle、IdleSeconds 待つ
      └ あれば   → Reset-ClaudeUsage → Invoke-WorkItem → トークン使用状況を1行
    catch
        作業ログに error、リースを外し、todo に戻す
        Get-ConsecutiveFailures >= MaxFailures (既定3) なら棚上げ (cancel_requested)
        ErrorBackoffSeconds (既定30) 待つ
```

**棚上げが要るのは恒久的な失敗があるから。** 残高不足やキー不正では、
戻して拾い直すのを延々と繰り返してしまう。3回で止めて原因を書き、
利用者が「中止を解除して要対応へ」で再開できるようにする。

### 記憶は待機中に1枚ずつ

閉じたカードから「次に効くこと」を覚える (`Update-MemoryFromClosedCards`) のは、
**カードが閉じたあと**でなければならない ―― 一番はっきりした材料は
利用者が最後に書くもの (差し戻しの指示・完了メモ) で、完了メモは閉じるときに書かれる。

**要対応のカードより優先度が低い。** 人が待っているのは目の前の1枚であって記憶の整理ではないので、
手が空いたときに進める。失敗したら間を置く (`$script:MemoryPauseUntil`) ――
キーが無いなどの恒久的な失敗を、待機のたびに叩き続けても何も進まない。

## 9. 不変条件

| # | 守っていること | 担保 | 破れたときの症状 |
|---|---|---|---|
| 1 | 出自を読まずに作業しない | ワーカーが先に取り直す + 取り直しを証跡に残す | 「元のメールを開いてご確認ください」で終わる報告 |
| 2 | 投稿先・宛先はモデルが決めない | カードの元通知から束縛して `Invoke-WorkTool` に渡す | 無関係な相手に届く |
| 3 | 名義は繋いだアカウントから決まる | `New-Viewer` + 出自のヘッダで立場を足す | 他人になりきった返信が出る |
| 4 | 既読にするのは読んだ分まで | `commentWatermark` | 作業中の指示が読まれずに消える |
| 5 | 送信済みは直しに回さない | `sentItems.Count` で分岐 | 同じ相手に二通目が出る |
| 6 | 送信後の指摘は赤く出し続ける | `tasks.alert` | 壊れたまま普通のカードとして埋もれる (#295) |
| 7 | `blocked` と `setup` を取り違えない | 元のカードは `blocked` | 資格情報を入れても二度と再開されない |
| 8 | `human_step` は DB から読む | クロージャは DB に書く | 結論が報告に出ず、検証にも渡らない |
| 9 | 恒久的な失敗は棚上げする | `Get-ConsecutiveFailures` | 同じカードで API を叩き続ける |
| 10 | 会話は捨てずに続ける | `Get-SessionPlan` | 前回何を書き込んだか知らないまま作業する (#295) |

## 12. いま抱えている歪み

- **`Invoke-WorkItem` が 750 行。** 束縛の取り出し (6 サービス) と、ツールの後始末 (`onTool`
  のクロージャ) と、検証のループが1つの関数に入っている。サービスを足すたびに前半が伸びる。
- **クロージャと外側の変数の関係が読みにくい。** `GetNewClosure()` が複製する値と、
  参照型なので共有される値 (`$sentItems`) が混在していて、#8 の事故はここから出た。
- **束縛の取り出しがサービスごとに直書き。** `raw_json` を読む / リンクを解釈する、が
  6 回繰り返されている。コネクタ側に寄せられる形だが、まだ寄せていない。
- **自己検証は必ず1往復ぶんの API を使う。** カードが増えるとそのまま費用になる。
  `-NoVerify` で切れるが、切ると #295 のような取り違えを誰も見なくなる。
