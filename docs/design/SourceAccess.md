# SourceAccess — 出自の取り直しと名義

`phase4/lib/SourceAccess.ps1` (605 行) / `phase4/lib/Viewer.ps1` (290 行)

カード1枚について、**作業を始める直前に**元のやり取りを取り直す。
同時に「このカードで**あなたは誰か**」を決めて渡す。

この2つは別々の問題に見えて、どちらも**同じ失敗の形**から来ている ――
**モデルに渡す材料が足りないまま、文面の読み方に判断を委ねていた。**

---

## 1. なぜ要るか

### 取り直し

これまで本文は同期した時点のものが全てで、ワーカーは足りなくても取り直せなかった。
実際の完了カードを洗うと、結果はほぼ全部これになっていた ――

> 「Gmail でスレッドを開いてご確認ください」
> 「そのセッションを開いてください」

**元通知を見ずに済ませるというこのアプリの前提と、正面から反する出力。**

取り直しは同期 (phase5) の仕事ではない。同期は「何が来たか」を落とさないための経路で、
1件を深く掘るのには向かない (全件に対して常時やるには重すぎる)。
**必要になった1枚についてだけ深く取る口**が別に要る。

### 名義

To: 他人 / Cc: 自分 で届いたメールで、ワーカーが**その他人の名義で**返信を下書きしていた。
読み手から見れば、頼んでもいない人が本人を名乗って返事をしてきたことになる。

原因は単純で、渡していたのがスレッド全文だけだったこと。
**「誰の代わりに書いているか」はどこにも書いていない**ので、本文の中で一番はっきり
「返事をする人」に見える To: の人に寄るのが、自然な読み方になってしまう。

## 2. 役割と境界

| | |
|---|---|
| 担う | 出自の取り直し (6 経路) / 添付の取り出し / 本文中のリンクの抽出 / 名義と立場の決定 |
| 担わない | いつ取り直すか (`Start-Worker`) / 実際の API 呼び出し (phase5 の各コネクタ) / 送信 |

`Viewer.ps1` には**ネットワークも資格情報も出てこない。**
ヘッダの文字列と繋いだアカウントの名前だけで決まるようにしてある ―― 試験しやすさのため。

依存: `phase5/lib/AccountStore.ps1` (どのアカウントか) と各コネクタ。

## 3. 取り直し (`Get-SourceContext`)

入口は1つで、`events.source` と `link` を見て経路を選ぶ。

| 経路 | 条件 | 取るもの |
|---|---|---|
| Gmail | `source='gmail'` | スレッド全文 / 添付 / `threadId` `messageId` `from` `to` `cc` |
| Outlook | `source='outlook'` | 同上 (Graph) |
| Teams | `link` が `msteams://` | チャットの会話 |
| Chatwork | `source='chatwork'` | 部屋の発言 |
| Backlog | `source='backlog'` | 課題とコメント |
| Slack | `link` が `slack://` | スレッドと添付 |
| Claude セッション | トーストの `title` から引く | 待機中の問いかけ |

### 返す形

```
ok           取れたか
kind         どの経路か
text         本文 (2万字で切る)
attachments  @{ id; name; mimeType; size }  ← id が fetch_attachment の引数になる
identifiers  モデルが http_request で叩くときの主キー類
links        本文中の https リンク (最大20)
note         取れなかった理由
viewer       このカードでの「あなた」
```

`links` を別に持つのは、**それがモデルにとっての「次に叩く先」**だから。
GitHub の招待 URL、確認リンク、ドキュメントの場所は本文の中にしか無い。

### 取れなかったときは、理由を返す

`ok=$false` でも例外にしない。`note` に理由を入れて返し、それがそのまま
作業プロンプトに載る ――「連携が未設定」「識別子が残っていない」「本文が空だった」。
**取れなかったことを黙ると、モデルは「本文はこれで全部」と思って書き始める。**

### アカウントは入口で束縛する

```
Use-EventAccount -Evt $Evt    ← 呼び出し側が忘れてもここで束縛される
```

忘れた場合の症状は「**別の人のメールが載る**」。
呼び出し側 (`Start-Worker`) でも束縛しているが、二重にしてある。

### Claude セッションだけ特殊

完了カードの最大勢力が「Claude のセッションが入力待ちです」という通知だった。
本文は 20 文字しかなく、**肝心の「何を訊かれているか」がカードに入っていない。**
何を足しても閉じられない。

ただしトーストの `title` はセッション名で、デスクトップ版が持つセッション一覧の
`title` と一致する。そこからセッション ID を引き、記録の末尾を読んで
「待機中の問いかけ」を取り出す。**API ではなくローカルのファイルを読む**唯一の経路。

## 4. 添付 (`Get-SourceAttachment`)

`attachments[].id` は `{経路}:{メッセージID}:{添付ID}` の形。
モデルはこの id しか指定できないので、**任意のファイルは取り出せない。**

```
作業フォルダに落とす
  名前は [IO.Path]::GetFileName() で畳む   ← パス区切り入りの名前でも外に出さない
テキストなら中身も返す
  拡張子で見て、無ければ MIME 型で見る      ← 添付には名前が付いていないことがある
  HTML なら ConvertFrom-HtmlToText を通す
```

## 5. 名義 (`Viewer.ps1`)

### 名義は1つ、本人は1人

**この区別がこのファイルの中心。**

| | 何で決まるか | 何に使うか |
|---|---|---|
| **名義** (`who`) | カードが届いたアカウント**1つ** | 誰の名前で書くか。返信もそこから出る |
| **本人** (`SelfNames`) | 繋いである**全アカウント** | そのメールの宛先が本人か |

全アカウントを見ないと、仕事用と個人用の両方を繋いでいる人が損をする ――
片方宛のメールがもう片方の受信箱にも届く (両方が宛先、転送、メーリングリスト) ので、
カードのアカウントのアドレスだけで見ると、**本人宛なのに「宛先は他人」と読んで
横で見ているだけの扱いにしてしまう。**

### 立場 (`role`) で既定の振る舞いが変わる

| role | 意味 | 既定 |
|---|---|---|
| `to` | 宛先は自分 | 自分の名義で返信する |
| `cc` | 返事を求められているのは自分ではない | **返信しない。** 報告に書いて閉じる |
| `from` | 自分が出したメールの続き | 相手の返答を待っている側 |
| `other` | 宛先に自分が出てこない (ML 等) | `cc` と同じ |
| `member` | メール以外 (Slack / Teams / …) | 会話の参加者 |
| `unknown` | 本人のアドレスが分からない | 名義を断定しない |

`cc` でも**本人として伝えるべきことがあれば横から入れる。**
そのときも**本人の名義**で入る ―― 他人の名義で書くことは無い。

### 分からないときは分からないと言う

ヘッダが引けなかったとき (スレッドだけ取れた等) は**立場を付けない。**
「Cc のはず」と当て推量するくらいなら、`unknown` のほうが害が小さい。
それでも**名義の束縛自体は必ず出す** ―― 名前が取れなくても
「他人の名義で書かない」は変わらないので、
`本人: (この連携先の接続に使っているアカウント本人)` と書く。

### プロンプトに載せる形 (`Get-ViewerBlock`)

**`<thread>` の外に置く。** 中は第三者が書いたデータなので、
そこに本人の情報を混ぜると「本文に書いてあること」と区別が付かなくなる。

```
あなたが代わりに手を動かしている本人 (名義):
  本人: me@example.com / 仕事用
  本人は Cc です。**返事を求められている相手は本人ではありません。**
  主たる宛先 (To): someone@example.com
  既定は「返信しない」。何が起きているかを報告に書いて閉じてください。
```

`Get-ViewerLine` は同じ情報の1行版で、**作業ログと画面に出す。**
「誰として書いたか」は、あとから報告だけを見ても分からない
(文面には本人の名前しか出てこない)。

## 6. 不変条件

| # | 守っていること | 担保 | 破れたときの症状 |
|---|---|---|---|
| 1 | 取り直しはカードのアカウントで行う | `Get-SourceContext` の入口で `Use-EventAccount` | 別の人のメールがカードに載る |
| 2 | 取れなかったら理由を返す | `ok=$false` + `note` | モデルが「本文はこれで全部」と思って書く |
| 3 | 名義は繋いだアカウントから決まる | `New-Viewer` / `New-MailViewer` | 他人になりきった返信が出る |
| 4 | 立場は全アカウントのアドレスで見る | `Get-SelfMailNames` | 自分宛なのに返さなくなる |
| 5 | 分からない立場は断定しない | `unknown` | 当て推量で Cc 扱いにして返信しなくなる |
| 6 | 名義は `<thread>` の外 | `Get-ViewerBlock` | 本文の記述と見分けが付かなくなる |
| 7 | 添付は id でしか指定できない | `{経路}:{メッセージID}:{添付ID}` | 任意のファイルを取り出せてしまう |
| 8 | 添付の名前は畳む | `GetFileName()` | 作業フォルダの外に書ける |
| 9 | 本文は上限で切る | `Limit-SourceText` (2万字) | 1枚の入力が膨らみ続ける |

## 8. いま抱えている歪み

- **`Get-SourceContext` が 350 行の分岐。** 経路ごとに「未設定か → 識別子はあるか →
  取る → 形を揃える」を6回繰り返している。コネクタ側に `Get-*Context` を生やして
  ここは束ねるだけにできるが、まだしていない。
- **Claude セッションの経路だけローカルのファイルを読む。** デスクトップ版の
  ファイル配置に依存していて、向こうが変われば黙って取れなくなる
  (`note` は出るので、症状は「本文が薄いカード」に戻るだけ)。
- **`identifiers` の鍵の名前が経路ごとにばらばら** (`threadId` / `chatId` / `issueKey`)。
  モデルには通じるが、呼ぶ側が共通の処理を書けない。
- **本文の上限 2万字が固定。** 長いスレッドは末尾が落ちる ――
  普通は新しい発言が下にあるので、**落ちるのは一番読みたいところ**になりうる。
