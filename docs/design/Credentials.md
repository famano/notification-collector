# Credentials — 資格情報と、接続の設定

`phase5/lib/SecretStore.ps1` (286 行) / `phase5/lib/AccountStore.ps1` (333 行) /
`phase5/lib/ServiceSetup.ps1` (1,338 行) / `lib/ApiKey.ps1` (102 行) /
`lib/AppConfig.ps1` (218 行)

**鍵をどこに置き、誰が入れ、どのアカウントのものとして使うか。**
この層が扱うのは3つの独立した問題で、混ぜると読めなくなる。

| | 問題 | 答え |
|---|---|---|
| `SecretStore` | どこに置くか | DPAPI で暗号化。**名前空間でアカウントを分ける** |
| `AccountStore` | 何人いるか | 名簿。**資格情報には触らない** |
| `ServiceSetup` | 誰がどう入れるか | 画面から入力 → 保存 → **疎通確認** |
| `ApiKey` / `AppConfig` | どこから取るか | 環境変数 → 保管庫 → 配布設定 |

## 1. 役割と境界

| | |
|---|---|
| 担う | 暗号化された保管 / アカウントの名簿と切り替え / 設定の入力欄の定義 / 保存と疎通確認 / OAuth・デバイスコードの手続き / 配布設定の取り込み |
| 担わない | 実際の API 呼び出し (各コネクタ) / 汎用 HTTP への注入 (`HttpAction`) / 画面 (`Start-Board`) |

**値を読み出す口を画面に作らない。** `ServiceSetup` が返すのは
「設定済みか」と「どのアカウントとして繋がったか」だけで、**トークンそのものは決して返さない。**

## 2. SecretStore — どこに置くか

### DPAPI (CurrentUser)

```
secrets.dat = DPAPI(JSON)  ←  同じ Windows ユーザーでログオンしていないと復号できない
```

平文の JSON に置かない。**トークンはメールボックスや Slack の全履歴への鍵そのもの**で、
リポジトリや同期フォルダに紛れ込むと影響が大きい。

さらに `Set-PrivateFileAcl` でファイルの ACL も絞る ――
**DPAPI は中身を守るが、ファイルの見え方までは変えない。** 既定では Users グループに
読み取りが継承されていることがあり、同じ PC の別アカウントに暗号文ごとコピーされうる。

**守れる範囲** (誤解しないこと):

> 守れるのは**別ユーザー・別 PC への持ち出し**と、置き場所の事故まで。
> **同じユーザーで動くプロセスからは守れない** ―― DPAPI の境界は
> 「ユーザーとマシン」であって「アプリケーション」ではない。管理者は所有権を取れる。

### アカウントは名前空間で分ける

**呼ぶ側 (コネクタ) は今までどおり書く。**

```
Get-Secret -Name 'slack.userToken'
    ↓ Resolve-SecretName が、いま選ばれているアカウントで読み替える
  1人目 → 'slack.userToken'      ← 接尾辞なし
  2人目 → 'slack.userToken#2'
```

**コネクタ側に一行も足さずに済む**のが狙いで、
「切り替えたつもりで前のトークンを使っていた」という失敗の形がそもそも生まれない。

**1人目に接尾辞を付けないのは移行を避けるため。** 既存の保管庫がそのまま1人目として読める ――
**移行の要る変更は、配った先で一番高くつく。**

### アカウントをまたいで共有する値

| 共有する | しない |
|---|---|
| `slack.clientId` / `clientSecret` | `ms.tenantId` (別テナントの職場アカウント) |
| `gmail.clientId` / `clientSecret` | `backlog.space` (別スペース) |
| `ms.clientId` / `clientSecret` | トークン類すべて |

同意画面に使うアプリ登録は**配る人が1つ用意するもの**で、繋ぐアカウントが増えても同じ。
ここまでアカウント単位にすると、2つ目を繋ぐときに「配布時に設定済み」が効かなくなり、
**利用者の手では取れない値を空欄として出すことになる**（永久に埋まらない欄）。

### 切り替えたらキャッシュを落とす

コネクタはアクセストークン・自分のユーザー ID・部屋名をモジュール変数に溜めている。
残ったまま切り替えると、**別のワークスペースの名前で別のワークスペースのメッセージを読む。**

```
Register-AccountReset -Service 'slack' -Handler { ... }   ← 持ち主であるコネクタが登録
Use-ServiceAccount -Service 'slack' -Id '2'               ← 変わったときだけ落とす
```

### 秘密と、秘密でない識別子を分ける

`Test-SecretConfidential` が見るのは、**漏洩検査 (`Test-SecretLeak`) を通すかどうか。**

OAuth のクライアント ID、テナント ID、Backlog のスペース名は、
**隠しても何も守れない値**で、相手に渡らなければ API が呼べない。
これを同じ扱いにすると**何も間違っていない呼び出しが止まる** ――
実際、スペース名 (`example.backlog.jp`) はホスト名そのものなので、
Backlog へのリクエストが全部「資格情報が含まれていた」として中止されていた。

**知らない名前は秘密として扱う。** 緩める側は必ず明示で書く。

## 3. AccountStore — 何人いるか

名簿だけを持つ。**資格情報には触らない。**

```
accounts.slack = [ {"id":"1","label":"仕事"}, {"id":"2","label":"個人"} ]
```

名簿も保管庫に置く ―― 資格情報ではないが、**資格情報と同じ寿命で消えてほしい**
(保管庫を消したのに名簿だけ残ると、中身の無いアカウントが画面に並ぶ)。

| 関数 | 要点 |
|---|---|
| `Get-ServiceAccounts` | 名簿が無ければ「1人目だけがいる」を返す。**空配列を返すと同期が一度も回らない** |
| `Add-ServiceAccount` | **ID は使い回さない。** 常に「今までで一番大きい数 + 1」 |
| `Remove-ServiceAccount` | 名簿から消し、**そのアカウントの秘密も消す** |
| `Use-EventAccount` | カードの出自から連携先とアカウントを決めて束縛する |
| `Reset-AccountSelection` | 選択を全部1人目に戻す (カンバン用) |
| `Get-AccountScopedKey` | watermark のキーも同じ付け方 (`sync.slack.lastTs#2`) |

**ID を使い回さない理由**: 消したアカウントの番号を次の人に与えると、
消し損ねた秘密や、そのアカウントで取り込んだイベントが**別人のものとして蘇る。**

**名簿だけ消さない理由**: 秘密が保管庫に残り続ける。
トークンは会話の全履歴への鍵なので、**使わなくなった時点で消す。**

**壊れた名簿は1人目に戻す。** JSON が読めなくても空にはしない ――
空にするより実害が小さい。

### 選択をいつ戻すか

| プロセス | 戻すか | なぜ |
|---|---|---|
| カンバン | **要求ごとに戻す** | 要求をまたいで生き続ける。1枚のカードのための切り替えが残ると、次の無関係な要求がその相手の資格情報で動く |
| ワーカー / 同期 | 戻さない | 「1枚 / 1アカウントを通し切る」形なので不要 |

## 4. ServiceSetup — 誰がどう入れるか

### なぜ画面に要るか

設定カードまでは出来ていた。ところがそのカードに書いてあったのは
**「`.\phase5\Connect-Service.ps1 -Service github` を実行してください」** ――
**カンバンの外に出ろ、という指示。**

このアプリは「カードはカンバンの上で閉じられる」を原則にしている。
送信も、実施も、人間の1手も画面で終わる。**設定だけが端末に戻されていた。**
しかも戻された先で待っているのは対話プロンプトで、常駐しているワーカーとは別のシェルが要る。
**止まっているカードが8枚あるときに、一番やりたくない形。**

だから「入力 → 保存 → 疎通確認」を**対話プロンプトに依存しない関数**にして、
`Connect-Service.ps1` (端末) とカンバン (画面) の両方がここを呼ぶ。

### サービスの定義 (`$script:SetupServices`)

画面はこれを読んで入力欄を組み立てる。

| 項目 | 意味 |
|---|---|
| `key` | **`Get-ServiceKey` (ホストから決まる正規名) と揃える。** 設定カードの `subject_key` が `setup:<key>` になる |
| `flow` | `token` (貼るだけ) / `oauth` (同意画面) / `device` (コードを出す) |
| `multi` | 複数アカウントを繋げるか |
| `required` | 無いとアプリが成立しないもの (Claude だけ) |
| `fields` | 入力欄。`secret=$true` は伏せ字で受け取り、**値は返さない** |

`multi = $false` にも理由がある。**Claude は連携先ではなくエンジン**で、
複数繋いでもさばける通知は増えない。**GitHub は通知の取り込み経路を持たない**ので、
「このカードはどちらのアカウントのものか」を決める手がかりが無い。

### 保存は、確認に失敗したら元に戻す

```
現在の値を控える
  ↓
Set-Secret
  ↓
Test-SetupConnection    実際に1回叩く
  ↓ 失敗
控えた値に戻す (元から無ければ消す)
```

**貼り間違えたトークンをそのまま残すと、「設定済みなのに全部 401」という
一番分かりにくい状態になる。**

確認の相手も固定する ―― ここで切り替えないと、
**別のアカウントのトークンで叩いて「繋がりました」と言う**ことになる。
`finally` で元のアカウントに戻すのは、途中で失敗したまま次の要求を捌くと
**そちらの資格情報を上書きする**から。

### 空欄の扱い

| 状況 | どうするか |
|---|---|
| 全部空 | 何もしない (押し間違いで設定を消さない) |
| 必須だが `keepIfEmpty` かつ設定済み | **空欄で通す** |
| 任意の欄が空 | 前の値を消さない |

`keepIfEmpty` が要るのは、**API キーは発行時に一度しか表示されない**から。
無いと、任意の欄 (管理 API キー) を後から足すたびにキーを貼り直すことになり、
それは実質「キーを作り直してください」と言うに等しい。

### 同じアカウントを二度繋がせない (`Get-SetupDuplicateNote`)

同意画面のせいで起きる ―― ブラウザに前のアカウントのセッションが残っていると、
**2つ目を繋いだつもりで1つ目をもう一度繋ぐ。**
画面上は成功するのにカードは1件も増えない ―― **原因が一番見えない失敗の形。**
繋いだ直後に名前で突き合わせて、その場で知らせる。

### 未接続を知らせるかどうか (`Get-SetupAttention`)

以前は未接続を全部数えてヘッダに出していた。だが **Claude 以外は「使っていないだけ」**
のことが多く、Backlog を使わない職場で「Backlog が未接続」と言い続けても意味がない。

```
warn = 未設定 かつ ( required                       ← Claude は黙らせられない
                   または (muted でない かつ (wanted または seen)) )

seen = 'card'          … そのサービスで実際にワーカーが止まった (設定カードがある)
       'notification'  … そのアプリの通知が実際に届いている
```

**利用者が「使う」/「警告しない」を決められる。** ただし `required` は黙らせられない ――
黙らせた結果が「**カードが1枚も増えない静かな日**」になる。

### 配る人が用意した値は、入力欄ごと隠す (`Test-SetupPreset`)

Google の OAuth クライアントも Slack のアプリも、**利用者の権限では作れない**ことが多い。
それを空欄として出すと、**そこは永久に埋まらないまま「未接続」が残る。**
用意済みなら入力欄を出さず、**押すだけの形**にする。

## 5. キーの取得元 (`ApiKey.ps1` / `AppConfig.ps1`)

```
1. 環境変数 ANTHROPIC_API_KEY   開発機。従来どおり最優先
2. 資格情報ストア (DPAPI)        カンバンの「接続」から入れたもの
3. 配布設定 app-config.json      配る人が同梱したもの
```

2 があるので**利用者は画面だけで入れられる**。3 があるので**配る人が入れておけば
利用者は何もしなくてよい。**

以前は 1 しか無く、**配った先ではそこが行き止まりだった** ――
設定し忘れると起動そのものが拒否され、画面すら出ないので**直し方も画面に出せない。**

**管理 API キーだけは配布設定から読まない。** これは組織の管理権限そのもので、
平文で同梱してよい種類のものではない (開発機のために環境変数だけは見る)。

### 配布設定は保管庫の「入口」

`Import-AppConfigSecrets` が起動時に DPAPI の保管庫へ取り込む。
**取り込んだあとは配布設定から資格情報を消してよい。**

**すでに保管庫に入っている項目は上書きしない** ―― 画面から入れ直した値が
次の起動で配布時の値に戻る、という一番分かりにくい壊れ方を避けるため。
**利用者が自分の値に切り替えたなら、それが最後に勝つ。**

**配布設定が守れないもの**:

> - **同じ Windows ユーザーで動くプロセスからは守れない** (平文 JSON も DPAPI も同じ)
> - **渡した相手からは守れない。** 同梱したキーは受け取った人が読んで他のアプリに貼れる
>
> ここに書いてよいのは「その人達と共有してよいキー」だけ。
> 嫌なら空のまま配り、各自に画面から入れてもらう。

## 8. いま抱えている歪み

- **`ServiceSetup.ps1` が 1,338 行で、その大半がサービス定義と help のテキスト。**
  画面に出す案内文がコードに埋まっているので、文言を直すとコードの差分になる。
- **サービスを足すときに触る場所が3つある** ―― `SetupServices` の定義、
  `Save-SetupCredential` の `switch`、`Test-SetupConnection` の `switch`。
  定義に「保存する関数」「確かめる関数」を持たせれば1つにできる。
- **`multi` が偽のサービス (GitHub) は、複数アカウントの筋道そのものが無い。**
  リポジトリの所有者で選ぶ別の仕掛けが要るので、いまは仕様として閉じている。
- **アカウントの選択がプロセス全体のモジュール変数。** 並行して別アカウントを扱えない
  (いまは1プロセス1枚ずつなので問題は出ていない)。
- **`Get-SetupAttention` の条件が4つの真偽値の組み合わせ。** 「なぜ警告が出ているか」を
  画面が説明するために材料を全部返しているが、読むのに一呼吸要る。
