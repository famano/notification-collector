# Connectors — 外部サービスとの接続 (共通の形と、サービスごとの差分)

`phase5/lib/GraphConnector.ps1` (1,076 行) / `GmailConnector.ps1` (555 行) /
`SlackConnector.ps1` (504 行) / `ChatworkConnector.ps1` (408 行) /
`BacklogConnector.ps1` (304 行) / `HtmlText.ps1` (18 行) /
`phase5/Sync-Sources.ps1` (612 行)

6つの連携先を扱うが、**立て付けは全部同じ**にしてある。
後段 (判定・カード・ワーカー) に経路ごとの分岐を持たせないためで、
違うのはサービス側の都合だけ。この文書は**共通の形を先に書き、差分を表で並べる。**

---

## 1. 共通の形

### 通知は起点、取りこぼしは watermark で埋める

```
通知 (phase1)   速い。が、PC が落ちていれば配信されず、wpndatabase は十数件しか持たない
    ↓ トリガ
同期 (phase5)   前回の続き (watermark) から読み直す。穴はこちらが埋める
```

**通知は低遅延のトリガに徹する。** 取りこぼしの無さは同期側が担保する ――
だから同期は「速さ」ではなく「**取り切れたと言えるか**」で作ってある。

### watermark は取り切れたときだけ進める

```
Get-StartPoint   settings の sync.{svc}.{key} を読む。無ければ 24 時間前 (BootstrapHours)
    ↓
取り込み          events に INSERT OR IGNORE (冪等)
    ↓
Set-SyncPoint     取り切れたときだけ書く。途中で失敗したら次回もう一度読み直す
```

**「一時的な失敗」と「何度読んでも直らない失敗」を分ける**のが共通の課題。

| | 例 | watermark |
|---|---|---|
| 恒久的 | 権限不足、チャンネルから抜けた、アーカイブ済み | **進める** (止めると読める分まで永久に取り込まれない) |
| 一時的 | レート制限、通信断 | **止める** (進めるとその範囲が取りこぼしになる) |

Slack ではこれを `$script:SlackPermanentErrors` の一覧で判定している。

### アカウントは連携先ごとに複数ありうる

仕事用と個人用の Gmail、二つのワークスペースの Slack、二つの Backlog スペース。
**片方だけ見たのでは、もう片方に届いたものはこのアプリを使っていないのと同じ**ところに戻る。

だから **watermark も、イベントの主キーも、掃き寄せの対象もアカウント単位**で分かれる
(`Get-AccountScopedKey` / `ConvertTo-AccountSourceKey`)。
**1人目だけは今までと同じキーを使う** ―― ここが変わると、次の同期が既定の 24 時間まで
巻き戻って大量のカードを立てる。

### 入口で絞る

会話に流れる全部をカード化すると、**判定 (LLM) のコストが跳ねる。**
だから同期の時点で「自分に関係があると言い切れるもの」だけに絞る。

| 種類 | 意味 |
|---|---|
| `dm` | DM / グループ DM |
| `mention` | 自分が名指しされたもの |
| `thread` | **すでにカードがあるスレッドへの返信** (会話の続き) |

絞りきれなかったものは捨てる。**ここを緩めると phase2 が全部 LLM に回す。**

### 本文の落とし方を1か所にする (`HtmlText.ps1`)

メールの本文は HTML にしか無いことがあり (Gmail / Outlook のどちらも)、
Teams に至っては**常に HTML で返る。**
落とし方が経路ごとに違うと、**同じ文面がカードによって別の見え方になる。**

### 読み取りと書き込みで扱いが変わる

どのコネクタも「読む関数」と「書く関数」を持つが、**書く側は必ず承認を通ってから呼ばれる**
(判定は `phase4/lib/WorkTools.ps1`)。コネクタ自身は承認を知らない ――
知っていると、呼ぶ側が増えたときに門を通らない道ができる。

## 2. サービスごとの差分

### 認証

| | 方式 | 保存するもの | 注意 |
|---|---|---|---|
| Google | OAuth ループバック (デスクトップ) | リフレッシュトークン | **「下書きだけ」のスコープが無い。** `compose` は送信も許す |
| Slack | OAuth (HTTPS の戻り先が要る) | **ユーザー**トークン | Bot は使わない (後述) |
| Microsoft | デバイスコード | リフレッシュトークン | **使うたびに新しい値に入れ替わる。保存し直さないと切れる** |
| Chatwork | API トークン1本 | トークン | ヘッダ名が `X-ChatWorkToken` |
| Backlog | API キー1本 | キー + スペース | **キーはクエリ文字列にしか載せられない** |

**Microsoft がデバイスコードなのは、登録の手間が一番軽いから** ――
リダイレクト URI を登録しなくてよく、クライアントシークレットも要らない
(保存すべき秘密が1つ減る)。さらに**カンバンを止めずに進められる**:
画面はコードを出し、ブラウザ側が数秒おきに聞きに来るので、サーバ側で待ち続けなくてよい。

**Backlog に汎用 HTTP の資格情報を注入しないのはこのため** ―― 注入するとモデルに見せる
URL にキーが載り、「トークンを URL に入れない」という全体の約束を破る。
**Backlog を叩くのはこのコネクタ経由だけ**にしてある。

### Slack は本人のトークン。Bot は増やさない

| | 理由 |
|---|---|
| 読む側 | 要るのは「**本人に届いたもの**」で、それは本人のトークンでしか見えない。Bot は招待されたチャンネルしか読めず、DM は Bot 自身宛しか見えない |
| 書く側 | **返信は会話の続き**なので、本人名義で出なければ相手に通じない。Bot 名義の返信は「誰かのアプリが代わりに喋っている」ように見える |
| 配る側 | Bot トークンは**配ってはいけない**ワークスペース共有の鍵。ユーザートークンは各自が同意して取るので、配る人が用意するのはアプリだけで済む |

ただし **Slack は OAuth の戻り先に HTTPS を要求する**ので、Google のように 127.0.0.1 へ
直接戻れない。そこで**転送しかしない静的ページを1枚だけ公開する** (`docs/slack-oauth-redirect.html`)。
通るのは単回・短命の認可コードだけで、引き換えに要る client secret は手元にしかない ――
**中継ページはトークンを一度も見ない。**

### 取り込みの形

| | 掃き寄せ | 絞り込み | 特徴 |
|---|---|---|---|
| Slack | `conversations.history` を会話ごと | dm / mention / thread | 通知のディープリンクに**API の主キーが全部入っている** |
| Gmail | `after:` で検索 | 受信トレイ | 何日落としていても穴が埋まる |
| Teams | `/me/chats` | ほぼ不要 | 出てくる時点で参加している会話 (チャネルは含まれない) |
| Outlook | 受信トレイ | 受信トレイ | Gmail と同じ形 |
| Chatwork | 部屋ごと | DM + メンション | **`force=0` は使わない** (後述) |
| Backlog | `/notifications` | **不要** | **自分宛の出来事だけがサーバ側で選ばれている唯一の経路** |

**Chatwork の `force=0` を使わない理由**: サーバ側が「前回の続き」を覚えているので、
二度目が空で返る。こちらの watermark と二重管理になり、
**同期が失敗した回のぶんが誰にも拾われないまま消える。**
`force=1` で直近を取り、`send_time` で自分で切る。
1回で取れるのは 100 件までで、**取り切れないときは watermark を進めない。**

**Backlog を既読にしない理由**: `markAsRead` はあるが、押すと**利用者の Backlog の画面から
お知らせが消える。** 同期が利用者の画面を書き換えてよい理由はない。

### Slack のリンクを揃える

掃き寄せで拾ったメッセージにも、**通知から来たものと同じ形のリンク**を作る
(`New-SlackLink`)。揃えておけば、スレッド全文の補完も permalink の取得も
**既存の経路がそのまま動く。**

## 3. Sync-Sources — 順番に意味がある

```
1. Slack の掃き寄せ    前回の続きから、関係のあるものをイベントにする
2. Slack の補完        slack:// を持つイベントにスレッド全文と permalink を足す
                       ← 1 が作ったイベントもここで埋まるので、掃き寄せが先
3. Gmail
4. Microsoft 365       Teams (掃き寄せ → 補完) → Outlook
5. Chatwork
6. Backlog             掃き寄せが要らない唯一の経路
```

どの経路も**繋がっているアカウントの数だけ回る。**
すべて冪等で、同じものを何度取り込んでも `events` の UNIQUE で弾かれる。

復旧用の入口が2つある。

| | 何をするか |
|---|---|
| `-Since` | watermark を無視して取り直す。**取りこぼしに気付いたとき** |
| `-GmailQuery` | 検索式を明示する。**手動の掘り起こしとみなし、watermark は動かさない** |

## 4. アクセストークンのキャッシュ

Google のアクセストークンは、**期限だけで判断してはいけない。**

```
キャッシュを使うのは「保存されているリフレッシュトークンが、引き換えたときと同じ」間だけ
```

再認可はカンバンのプロセスで行われ、**ワーカーと収集は別プロセス**で動いている。
期限だけを見ていた頃は、カンバンで Calendar のスコープを足して取り直しても、
ワーカーは最大1時間古いトークンを使い続けていた ―― その間 Calendar は 403、
Google 側で許可を取り消していれば 401 になり、「**設定したのに直らない**」ように見えていた。
**保存先は共有なので、そこを見れば気付ける。**

同じ理由で、`http_request` が Google に 401 を食らったら
`Clear-GmailAccessToken` を呼ぶ (次の呼び出しでリフレッシュトークンから取り直す)。

## 5. 不変条件

| # | 守っていること | 担保 | 破れたときの症状 |
|---|---|---|---|
| 1 | 取り切れたときだけ watermark を進める | 各同期の末尾で `Set-SyncPoint` | 失敗した範囲が**誰にも拾われずに消える** |
| 2 | 恒久的な失敗では watermark を止めない | `Test-SlackPermanentError` ほか | 読める会話の分まで永久に止まる |
| 3 | 1人目の watermark キーは変えない | `Get-AccountScopedKey` | 24 時間まで巻き戻って大量のカードが立つ |
| 4 | 入口で「自分に関係がある」に絞る | dm / mention / thread | 判定のコストが跳ねる |
| 5 | 取り込みは冪等 | `events` の UNIQUE | 再実行でカードが増殖する |
| 6 | HTML の落とし方は1か所 | `HtmlText.ps1` | 同じ文面がカードによって別の見え方になる |
| 7 | Backlog の鍵を汎用 HTTP に注入しない | `CredentialHosts` に書かない | URL とログにキーが残る |
| 8 | Backlog を既読にしない | `markAsRead` を呼ばない | 利用者の画面からお知らせが消える |
| 9 | Slack は本人のトークン | ユーザートークンのみ | DM が読めない / 返信が Bot 名義で出る |
| 10 | Microsoft のリフレッシュトークンは毎回保存し直す | 引き換え後に保存 | しばらく動いたあと突然切れる |
| 11 | アクセストークンのキャッシュは元の値で判定 | `$script:GmailTokenSource` | 設定し直しても最大1時間直らない |
| 12 | 掃き寄せのリンクは通知と同じ形 | `New-SlackLink` | 補完と permalink の経路が動かない |

## 7. いま抱えている歪み

- **`GraphConnector.ps1` が 1,076 行で、Outlook と Teams が同居している。**
  認証の入口が同じなので1本にしてあるが、読む側からは2つのサービスに見える。
- **掃き寄せの形が6回繰り返されている。** 「一覧を取る → 会話ごとに読む →
  絞る → イベントにする」が、少しずつ違う形でコネクタごとに書かれている。
  共通の骨を切り出せるが、サービスごとの例外 (Chatwork の `force`、Backlog の
  `/notifications`) が多く、抽象化すると例外のほうが読みにくくなる。
- **`Sync-Sources.ps1` が1本の長い手続き。** 経路を足すたびに伸びる。
- **絞り込みの規則がコネクタの中にある。** 「何を自分宛とみなすか」は方針なので
  `policy.json` 側にあってもよいが、いまはコードを直すしかない。
- **`ConvertFrom-HtmlToText` は正規表現。** 崩れた HTML では本文が混ざることがある
  (症状は「カードの本文が読みにくい」で、止まりはしない)。
