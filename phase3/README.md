# Phase 3 — カンバンボード UI

タスクストアを**ユーザーが操作できる**ようにする層。割り込み・修正・新規起票をここで行う。

| ファイル | 役割 |
|---|---|
| `Start-Board.ps1` | `HttpListener` によるローカル Web サーバと JSON API |
| `wwwroot/index.html` | UI 一式（依存ライブラリなし・単一ファイル） |
| `lib/SetupFlow.ps1` | 資格情報が入った直後の後始末（止まっていたカードを動かす） |

## 使い方

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\phase3\Start-Board.ps1
```

ブラウザが `http://localhost:8787/` で開く。`-Port` で変更、`-NoBrowser` で自動起動を抑止、
`-DbPath` で別の DB を見る。`-OutputRoot` はワーカーの作業フォルダの親
（既定 `phase4\output`。「フォルダを開く」の行き先になる）。
管理者権限は不要（localhost へのバインドは URL 予約なしで通る）。

## できること

| 操作 | 挙動 |
|---|---|
| カードをドラッグ | 列を移動。`version` を添えて送るので競合したら 409 で拒否される |
| **実行中から外へドラッグ** | `cancel_requested` が立つ。**これが割り込みの信号** |
| カードをクリック | 詳細ドロワー。**ワーカーの報告**・成果物・出口・判定理由・作業ログ・元の通知 |
| **「ワーカーの報告」** | ドロワーの先頭に**書式のまま**出る。見出し・箇条書き・表・引用・コード |
| 「元を開く ↗」 | 元のメッセージを別タブで開く。カードの右下と、ドロワーの見出し横に出る |
| **「この後どうするか」** | 出口は3つ。**承認して終了 / 差し戻す（＋指示） / 自分で対応して終了** |
| **「送る」** | 返信先があるカードでは「承認」がこれになる。**送って完了**と**送って作業を続ける**の2つ |
| **「返信先の内容」** | 送る欄のすぐ上。誰がいつ何と言ったかを発言ごとに割って出す |
| **「フォルダを開く」** | 成果物のあるカードで出る。作業フォルダをエクスプローラーで開く |
| 「下書きを保存」 | まだ閉じないとき。`user_edited` に入り、`agent_output` は上書きしない |
| 「報告を取り込む」 | ワーカーの報告を「対応の記録」にコピーして手直しする |
| 「作業を中止」 | `cancel_requested` を立てる |
| 指示 | `task_comments` に積む。ワーカーは次の実行前にこれを読んで方針を立て直す |
| 「アーカイブ」 | ボードから隠す。ヘッダの「アーカイブ」から一覧・復元できる |
| 「削除」 | 確認のうえ完全削除。作業ログとやりとりも消える |
| 「まとめて削除」 | 完了・対応不要・アーカイブ済みの見出しに出る。その列のカードを確認のうえ一括で完全削除 |
| 「+ カード」 | 通知に紐づかないカードを手で起票 |
| **「このアプリは今後不要」** | カードの「片付け」に出る。そのアプリを以後ふるいで落とし、カードは対応不要へ |
| **「接続」** | 外部サービスの資格情報をこの画面で入れる。知らせるべき未接続 (Claude・使うと選んだもの・通知が来ているもの) の数がボタンに出る |
| **「方針」** | ふるい分けの条件と、判定に渡す背景情報（名前・役割・優先事項）を直す |
| 「?」 | 列とラベルの意味を説明するパネル |

ヘッダにはワーカーの状態（作業中 / 承認待ち / 待機中 / 停止中 / エラー）と、
いまどのカードで何をしているかが出る。処理中のカードは枠が緑になる。

止まっている常駐があれば、ボード上部に赤い帯で出す。止め方が2種類あるので別々に見る。

| 止まっているもの | 起きること | 帯の内容 |
|---|---|---|
| 収集 (`Start-Collector.ps1`) | 新しいメールも通知もカードにならない | 「取り込みが止まっています」 |
| ワーカー (`phase4\Start-Worker.ps1`) | カードは増えるが誰も着手しない | 「要対応のカードには誰も着手しません」 |

収集が止まっているときの見え方は「要対応が 0 件」であり、
**何も来ていない状態と見分けが付かない。** だから静かなときほど明示する必要がある。
死活は収集が `settings` の `collector.*` に、ワーカーが `worker_state` に書く。
トリアージは 1 件ずつ LLM を呼んで数分かかることがあるので、
収集の「止まった」判定はワーカー (90 秒) より長い 15 分にしてある。

## 判断の方針もここで直す

`policy.json` のふるい分けと背景情報は、**気付いた場所で直せないと直されない。**
「この通知は今後要らない」と分かるのはカードを見た瞬間で、そのとき開いているのは
カンバンである。別のアプリでファイルを開いて JSON を編集して保存して……となると、
たいてい直されないまま同じ通知が毎回 LLM に流れ続ける。

- カードの「片付け」→ **「このアプリは今後不要」**。条件は**サーバがカードの元通知から取る**
  （画面から任意の条件を送れる作りにはしない。ボードに載った第三者の文面から
  「全部無視」に近い条件を仕込む道ができるため）
- ヘッダの **「方針」** → 条件の一覧と削除、手での追加、背景情報の編集
- `*` だけのようなすべてに一致する条件は弾く。1つ入ると以後すべての通知が黙って捨てられる
- 効くのは次のトリアージから

## ツール実行の承認

ワーカーが危険なツール（コマンド実行・外部通信・作業フォルダ外への書き込み）を
使おうとすると、ボード上部に承認パネルが出てワーカーは停止する。

**実行内容は省略せずに表示する。** コマンド本文や URL がそのまま出る。
通知やメールの本文がワーカーの入力に混ざる以上、ここが注入と実行のあいだに立つ
唯一の壁になるため、要約で済ませてはいけない。

選べるのは、許可 / 拒否 / このカードでは以後許可 / 今後すべて許可。
「まとめて許可」はヘッダ下に一覧として残り、`×` でいつでも取り消せる。
ヘッダの「自動承認」ボタンで YOLO にもできる（有効化時に何が起きるか確認を出す）。

## レビューで読むのはワーカーの報告

使ってみて分かったのは、**カードを開いてから実際に読むのはワーカーの報告だけ**だということ。
判定理由も作業ログも、報告に不審なところがあったときにしか開かない。

にもかかわらず報告は折りたたみの中にあり、しかも記号のまま出していた。
`## 見出し` `- 箇条書き` `| 表 |` が素のテキストで並ぶので、長い報告ほど読めない。
**一番読まれる文章が、一番読みにくい形で置かれていた。**

いまは、

- ドロワーの先頭に**畳まずに**出す（毎回開くものを畳んでおく意味はない）
- 見出し・箇条書き（入れ子とチェックボックス）・表・引用・コード・区切り線・強調を
  **書式のまま**描く

**書式を付けても `innerHTML` は使わない。** 報告はモデルが書いた文字列で、そこには
第三者の文面が引用として混ざる。描画は全要素 `createElement` + `textContent` のままで、
知っている記法だけを要素に変え、知らないものは文字として出す。生の HTML は素通ししない。
リンクだけは `http / https / mailto` の許可制にし、それ以外は飛び先を文字列で見せる。

同じ描き方をワーカーの発言（やりとり）と `.md` の成果物にも使う。書かれているものが
同じ性質のものなら、読む形も同じでよい。

## カードの出口

報告を読んだあとにすることは3つしかない。

| 出口 | 何が起きるか |
|---|---|
| **承認して終了** | ワーカーの報告の内容で了とし、完了へ。ひとこと残せる |
| **差し戻す（＋指示）** | 指示を `task_comments` に積み、要対応へ戻す。ワーカーがやり直す |
| **自分で対応して終了** | 対応の記録を書いて完了へ。空のままでもよい |

以前はこれらを横一列のボタンとして並べていた。**どれが「終わらせる」もので、どれが「戻す」
ものなのかが、押す前に読み取れない。** いまは先に道を選び、その道に要る欄だけを出す。

まだ報告の無いカードでは「差し戻す」は「指示を送る」になる。戻す先の仕事がまだ無い。

### 送るカードだけは「承認」が「送る」になる

返信先がカードの元イベントから束縛できるカードでは、**送ることが承認そのもの**なので
「承認して終了」は出さない。代わりに、送信側に事情がある。

**送信は終わりとは限らない。** メールの中身が作業依頼なら「承知しました」と返してから
作業が始まるし、作業が終わっているなら送って閉じる。後者しか無いと、前者のカードは
送った瞬間に完了へ落ちて行方が分からなくなる。だから出口を2つ持たせた:

| ボタン | 送信後 |
|---|---|
| **送って完了** | 完了へ（`finish` の既定） |
| **送って作業を続ける** | **要対応へ戻す。** 続きの指示も任意で一緒に積める |

送らずに閉じたいとき（ワーカーが既に送っていた、電話で済ませた）は
「自分で対応して終了」を使う。

### 送る前に、相手が何と言ってきたかを読む

**文面のトーンは文脈でしか決まらない。** 返信先の内容が読めないと書いたものに自信が持てず、
結局は元のメールを開き直すことになって「カンバンだけで完結する」が崩れる。
送る欄のすぐ上に、**誰がいつ何と言ったか**を発言ごとに割って出す。

割るのはサーバ (`Get-EventConversation`)。`events.body` の形（メールは
「差出人:／宛先:／Cc:／日時:」に続けて本文、Slack は「--- 誰 / いつ」で始まる発言の連なり）を
決めているのは Phase 5 なので、画面でも切り分けると形を知っている場所が2つに増える。

**相手の文面には書式を付けない。** 第三者が書いた URL を押せる形にすると、見えている文字と
飛び先が違うものを作れてしまう。整えるのは並びだけにする。同じ割り方は「元の通知」でも使う
（未接続で送り先が取れないカードでも、元の文面は読める形で出る）。

### 成果物はフォルダで開く

成果物が要るカードは、中身を眺めて終わりではなく**ファイルを触る**ことになる。
1枚ずつ「中身を見る」で開くだけでは足りないので、作業フォルダをエクスプローラーで開く
ボタンを出す。開く先は**サーバが DB の記録から決める**（成果物の中身を返す口と同じ扱いで、
クライアントからパスは受け取らない）。成果物がまだ無くても、フォルダがあれば開ける。

### 出口の欄は、押せば必ず何かが起きる

**以前の「自分の下書き / 修正」は出口を持っていなかった。**
保存しても起きるのは「次の実行時にプロンプトへ渡る」だけで、実際に外へ出るのは
ワーカーが書いた `.eml` や Gmail 下書きだった。つまり欄を直しても成果物は変わらず、
直したければ結局コメントで指示してワーカーに書き直させることになる。
使われなくて当然で、欄のほうが間違っていた。いまは**書いた内容がカードを閉じる操作に
直結する**（送る／完了にする）。

「自分で対応」側の欄を「メモ」と呼ばないのは、そこに書かれるのが**「なぜ自分はこれを完了に
したのか」**だから。カンバンで完結するというのは、通知欄を見ないことに加えて、
後からその判断を辿れることでもある。

テキストは3つに分けて持つ。役割が違うものを1つの箱に入れない:

| カラム | 中身 | 上書き |
|---|---|---|
| `agent_output` | 何をしたか・何を確認すべきかの報告 | 実行のたびに |
| `draft_text` | ワーカーが提案する、外に出る文面 | 実行のたびに |
| `user_edited` | **利用者が確定させた版。これが実際に送られる** | **しない** |

欄は `user_edited ?? draft_text` を出す。ワーカーが何度作り直しても、
手を入れた内容は消えない ―― 元からの設計方針をそのまま維持している。

**空のまま完了にしても `user_edited` は消さない。** 送る文面と対応の記録は同じ列に入るので、
「送らずに完了」を選んだだけで書きかけの文面が消えると取り返しがつかない。

**送信は、モデルではなく人が押す操作。** 取り消せないので条件を厚くしてある:

- **宛先はサーバがカードの元イベントから決める。リクエストの宛先は受け取らない。**
  受け取れる作りにすると、ボードに載った第三者の文面から宛先を差し替える道ができる
- `confirm` が無いと送らない（UI の確認ダイアログを通った印）
- 送る文面は先に `user_edited` へ保存する。送ったものと残るものを一致させる
- `version` を照合する。画面が古いまま押したら 409 で止める
- 送信後は作業ログに `sent` として残り、カードは完了（または要対応）へ移る

## 設定カードの出口

**設定カードだけが、カードの中から画面の外へ出す指示だった。**
書いてあったのは「`.\phase5\Connect-Service.ps1 -Service github` を実行してください」――
常駐しているシェルとは別に窓を開き、対話プロンプトに答えろ、という意味である。
止まっているカードが8枚あるときに一番やりたくない形をしている。

いまは設定カードを開くと入力欄が出て、次の3つがその場で終わる:

1. **保存** — DPAPI で暗号化して保存する（値は画面に戻らない）
2. **疎通確認** — 実際に1回叩いて、誰として繋がったかを出す。
   失敗したら**元の値に戻す**。貼り間違いを「設定済み」にしない
3. **再開** — その設定を待って止まっていたカードを「要対応」に戻し、
   設定カード自身を完了にする

3 が無いと設定カードは半分しか働かない。「1枚直せば同種がまとめて通る」が
狙いなのに、8枚を手で戻すことになる。台帳の「このサービスは未設定」も同時に
打ち消す ―― これはワーカーに毎回渡るので、残っていると設定後も
「権限が無い前提」で計画を立てる。

カードが無くても繋げるように、ヘッダの「接続」からも同じ欄を出す。
未接続の数がボタンに出るので、「設定さえすれば進むカードが溜まっている」ことに気付ける。

**ただし、数えるのは「要る」と分かっている未接続だけ。** Claude 以外は使っていないだけの
ことが多く、全部を数えると数字が常に出て読まれなくなる。数えるのは:

- 無いと動かないもの (Claude)。黙らせられない
- 利用者が「使う」を選んだもの。一度繋いだものは自動でこれになる
- 直近 30 日にそのアプリから通知が届いているもの (`events.source = 'notification'` の AUMID / 表示名)
- 設定カードが立っているもの (ワーカーが実際にその権限不足で止まった)

あえて繋がないこともあるので、Claude 以外は「このサービスは警告しない」で黙らせられる
(`POST /api/setup/<key>/attention` に `{ "muted": true }`)。選択は DB の `settings` に置く ――
資格情報ではないので保管庫には入れない。

**Google の同意画面は、戻り先をカンバン自身にする。**
`Connect-Service.ps1` は専用の `HttpListener` を立てて `GetContext()` で待つが、
カンバンは1本のループで要求を捌いているので、そこで待つと画面ごと固まる。
戻り先を `/oauth/google/callback` にすれば、同意の戻りはただの1リクエストとして流れる。
（Google のデスクトップ クライアントはループバックへのリダイレクトを任意のポートで許す）

**Microsoft 365 は画面にコードを出して、済んだかを聞きに来てもらう。**
デバイスコードフローはリダイレクト URI を1つも登録しなくてよい（テナントの
設定で止まりにくい）代わりに、「サインインが済んだか」を誰かが聞き続ける必要がある。
ここでも待つのはサーバではなくブラウザ側にする ―― `/api/setup/<key>/devicecode` で
コードを出し、`/api/setup/<key>/poll` を数秒おきに叩く。1リクエストずつ流れるので
画面は止まらない。繋がった時点で、止まっていたカードの再開まで同じ経路で終わる。

**値を読み出す口は作らない。** `/api/setup` が返すのは「設定済みか」と
「どのアカウントとして繋がったか」だけで、トークンは決して返さない。

## 設計上の判断

**状態を変える要求は `Origin` も見る。**
ボードから送信できるようにした以上、`Host` の検証だけでは足りない。
ブラウザは別サイトからの POST に必ず `Origin` を付けるので、外のページが
`localhost:8787` を叩いて削除や送信を起こす経路をここで塞ぐ（GET は対象外）。

**SSE ではなくポーリングにした。**
当初は SSE を想定していたが、PowerShell 5.1 の `HttpListener` は単一スレッドで回るため、
接続を張りっぱなしにするとリクエストループが止まる。ランスペースを使えば回避できるが、
一人で使うローカルボードには複雑すぎる。代わりに**安い `/api/rev`（件数と最終更新時刻）を
1.5 秒間隔で叩き、変化したときだけボード全体を取り直す**方式にした。

**入力中はドロワーを再描画しない。**
ポーリングで再描画すると、入力途中のコメントや下書きが消える（実装中に実際に踏んだ）。
`drawerBusy()` でドロワー内にフォーカスがあるかを見て、その間は作り直さない。
ボード側は更新されるので、他の変更は見える。

**表示は必ず `textContent`。**
カードには Slack のメッセージ本文がそのまま載る。`innerHTML` を使うと第三者のメッセージから
DOM を注入できてしまうため、UI は全要素を `createElement` + `textContent` で組んでいる。
報告に書式を付けるようになっても、ここは変えていない。Markdown の描画も同じ組み方で、
知っている記法だけを要素に変え、生の HTML は素通ししない（`<script>` も `<img onerror=…>` も
文字として出る）。**書式を出すために `innerHTML` に戻す、という取引はしない。**

**元のメッセージへのリンクだけは踏めるようにし、スキームを許可制にした。**
当初はリンクも文字列として出すだけにしていたが、それでは元の会話を確かめるのに
URL をコピーして貼り直すことになり、「カンバンだけで完結する」という前提が崩れる。
いまはカードの右下と、ドロワーの見出し横に「開く」を出す。

踏ませる以上、危ないのは本文ではなく `href` なので、そこだけ絞る:

- スキームは `https / http / mailto / slack / msteams` の許可制。`javascript:` `data:`
  `file:` は入り口で落とす。判定はサーバ (`Get-SafeOpenLink`) とクライアントの両方で行う。
- 制御文字や空白を含む URL は弾く。改行でスキーム判定をすり抜ける細工があるため。
- 表示するラベルは常に自前で決める（`Slack で開く` など）。通知が持ってきた文字列を
  リンクの見た目にはしない。飛び先そのものは「元の通知」の中に別途、文字列として出す。
- `target="_blank"` + `rel="noopener noreferrer"`。

Slack は Phase 5 の補完時に `chat.getPermalink` の結果を `events.permalink` に残してあり、
それがあれば `slack://` ではなく https の permalink を開く。

**127.0.0.1 のみにバインドし、`Host` ヘッダも検証する。**
ボードには業務上のメッセージが載るので外部に露出させない。

**生の enum を画面に出さない。**
`doing` `normal` `v20` のような内部値をそのまま出すと意味が伝わらない（実際に指摘を受けた）。
`列 実行中` `緊急度 中` `版 20` のようにラベルと日本語値で表示し、
各ラベルに説明を tooltip で付け、「?」パネルに一覧を置いた。

**操作の結果を必ず画面で返す。**
ボタンは押した瞬間に無効化して「保存中…」に変わり、完了時に緑（成功）か赤（失敗）の
トーストを出す。押しても何も起きないように見える状態を作らない。

**強弱をつける。**
全部を同じ濃さで出すと、どこを見ればいいのか分からなくなる（実際に指摘を受けた）。
いま強調しているのは、カードのタイトル、緊急度「高」、成果物の有無、
着手されない状態の警告だけ。ID・種別・版といった補助情報は小さく淡い一行にまとめ、
緊急度はタグではなくカード左端の色帯で示している。
列も、見るべき列（要対応・実行中・レビュー待ち）だけ色を持たせ、
完了と対応不要は沈めている。

**長くなるものは既定で畳む。ただし毎回読むものは畳まない。**
開いた直後に見えるのは「**ワーカーの報告**」「成果物」「この後どうするか」の3つ。
判定理由・試したこと・作業ログ・やりとり・元の通知は折りたたみで、開閉状態は
カードを開き直しても保たれる。報告を折りたたみから出したのは、**畳む理由が
「長いから」で、開く回数が「毎回」だったから** ―― その2つが揃うなら畳む側が間違っている。

**指示欄は複数行。**
`input` だと改行が打てず Enter が即送信になっていた。`textarea` にして、
Enter は改行、送信は Ctrl+Enter か「差し戻す」ボタンにした。
表示側も `white-space: pre-wrap` で改行を保つ。

**指示を書く欄は1つだけにする。**
以前は「やりとり」の折りたたみにも入力欄があり、出口のボタンとは別にカードを
要対応へ戻していた。同じことをする欄が2か所にあると、どちらがカードを動かすのか
分からない。いまは「差し戻す」に1つだけ置き、「やりとり」は履歴（新しい順）にした。

**入力中の文字は、画面を作り直しても消さない。**
ドロワーは 1.5 秒ごとの更新でも、出口のタブを切り替えても作り直される。
書きかけをサーバの値で上書きすると指示や文面が黙って消えるので、カード id ごとに
手元へ控え、作り直しのたびに戻す。サーバに入った時点で控えは捨てる。

**一括削除は、押した時点の列をサーバ側で確かめ直す。**
ボードは 1.5 秒ごとに更新される。画面が古いまま「まとめて削除」を押すと、
その間に別の列へ移ったカードまで消えかねない。UI は見えている id を送るが、
サーバはその id のうち**いまその列にあるものだけ**を消し、残りは `skipped` として返す。
削除自体は 1 トランザクションで行うので、途中で外部キーに引っかかっても
「何枚かだけ消えた」状態にはならない。出すのは片付いた列（完了・対応不要・
アーカイブ済み）だけで、未分類や要対応には出さない。まだ見ていないものを
一掃できてしまうため。

**成功を名乗る前に応答を見る。**
削除が外部キー制約で失敗しているのに「削除しました」と表示していた（実際に踏んだ）。
状態を変える操作は、ステータスと `ok` を確認してからトーストを出す。

**パネル外のクリックで閉じる。**
ただしカードの上は除く（別のカードへの切り替えとして扱う）。
未保存の編集があるときだけ確認を挟む。

## 検証済みの範囲

ブラウザで実際に操作して確認した:

- ボードの描画、詳細ドロワーの表示
- 下書きの保存 — `user_edited` に入り、`agent_output` は変化しない
- **カードの出口** — 返信先があるカードで「送る文面」と宛先が出ること、
  無いカードで「対応の記録」が出ること。「これで完了にする」で本文が保存され、
  作業ログに残り、カードが完了へ移ることをブラウザで実際に操作して確認
- **送信の門** — `confirm` 無し / 本文が空 / 送り先が無いカードは 400、
  古い `version` は 409、外部 `Origin` からの POST は 403 になること
- **元のメッセージへのリンク** — カードとドロワーに出ること、
  `href` が `rel="noopener noreferrer"` 付きで許可スキームのみになること
- **楽観ロック** — 古い `version` での移動は 409 で拒否、正しい `version` は 200
- **割り込み** — 実行中から他の列へ移すと `cancel_requested=1` が立つ
- コメントの投稿と表示
- **入力保護** — 外部から DB を更新して再描画を発火させても、入力中のコメントは消えない
  （ボードの表示は更新される）
- **XSS** — `<img onerror=...>` を含むタイトルは文字列として描画され、要素は注入されない

出口を作り直したときに確認した:

- **報告の書式** — 見出し・入れ子の箇条書き・チェックボックス・表・引用・コード・
  区切り線・強調・リンクが、報告のとおりに描かれること
- **書式を付けても注入されないこと** — `<script>` `<img onerror=…>` を含む報告で
  `img / script / iframe` が 1 つも生えず、`javascript:` のリンクは押せる形にならず
  飛び先が文字列で出ること。`.md` の成果物とワーカーの発言でも同じ描画を使う
- **出口の3つ** — 承認して終了 / 差し戻す / 自分で対応して終了 が選べ、
  それぞれ `approve` / `comment` / `done` に飛ぶこと。承認は完了へ移り、作業ログに残る
- **送信の2つの出口** — 「送って完了」は `finish:true`、「送って作業を続ける」は
  `finish:false` で飛び、後者は続きの指示を `comment` として積むこと
- **返信先の内容** — メールが差出人・宛先・Cc・日時と本文に割れ、Slack がスレッドの
  発言ごとに割れること（サーバの応答とブラウザの表示の両方）
- **作業フォルダ** — 成果物のあるカードで場所が返ってボタンが出ること、
  フォルダの無いカードは 404 になること
- **入力の保持** — 出口のタブを切り替えても、書きかけの文面と指示が残ること

追加で確認したこと:

- ワーカー稼働中にヘッダが対象カードと作業内容を表示し、該当カードが緑枠になる
- 保存ボタンが押下時に無効化＋「保存中…」になり、完了時に成功トーストが出る
- アーカイブでボードから消え、アーカイブ一覧に現れ、復元でボードに戻る
- 削除後は詳細取得が 404 になる
