# Phase 4 — ワーカー

`要対応` のカードを拾って下書きを作り、`レビュー待ち` に置く。

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\phase4\Start-Worker.ps1
```

`-Once` で1周だけ実行。`ANTHROPIC_API_KEY` が必要。

## 何をきっかけに動くのか

**イベント駆動ではなく、常駐プロセスのポーリング**です。カードを作ったり動かしたりしても
通知は飛びません。5秒ごとに DB を見て、拾えるカードがあれば処理します。

**ワーカーを起動していない限り、何をしても動きません。** カンバンは別プロセスなので、
ボードを開いているだけでは作業は進みません。

拾う条件（[`Get-NextWorkItem`](../phase2/lib/TaskStore.ps1)）:

| 条件 | 内容 |
|---|---|
| 列 | `要対応`、または**リースが切れた** `実行中`（落ちたワーカーの後始末） |
| 中止要求 | `cancel_requested = 0` であること |
| アーカイブ | されていないこと |
| 順序 | 緊急度（高→中→低）、次に ID の昇順 |

つまり以下は**動きません**:

- `未分類` `レビュー待ち` `完了` `対応不要` にあるカード
- 中止要求が残っているカード（`要対応` にあっても飛ばされる）
- 既存カードの本文を編集しただけ（再実行はされない）

もう一度やらせたい場合は、カードを `要対応` にドラッグしてください。
このとき中止要求は自動で解除されます。

## 失敗の扱い

例外が出たカードはリースを外して `要対応` に戻します。ただし**同じカードで3回続けて
失敗したら棚上げ**し（中止要求を立てて対象外にする）、理由を作業ログに残します。
残高不足やキー不正のような恒久的な失敗で、同じカードを永久に拾い直し続けるのを
防ぐためです。原因を解消したあと「中止を解除して要対応へ」で再開できます。

失敗直後は30秒待ってから次に進みます（API 側の問題を叩き続けないため）。

## 1枚のカードを処理する流れ

```
要対応 → [リース取得] → 実行中 → 未読の指示を読む
                                    ↓
                       Claude がツールを使って成果物を作る（複数ターン）
                                    ↓
                       報告を agent_output に保存 → レビュー待ち
```

**ツールを実行する直前ごと**に中止要求を確認する。生成が終わった直後にも確認し、
途中でユーザーが中止していれば結果を捨てる。ツール実行は1カードあたり
`-MaxTurns`（既定12）ターンまで。

## 実際にできる作業

文面をテキストで返すだけでなく、ツールで**実際に成果物を作る**。

| ツール | 内容 |
|---|---|
| `create_email_draft` | メールの下書きを `.eml` として作成。メールソフトで開くと下書きになる |
| `write_file` | 報告書・メモ・一覧などのテキストファイルを作成 |
| `read_file` / `list_files` | 自分が作ったファイルを読み返す |

成果物は `phase4/output/task-NNNN/` に出る。カンバンのカード詳細に一覧が出て、
その場で中身を確認できる。

### 送信はしない

`.eml` は**ファイルとして作るだけ**で、送信は人間がメールソフトで行う。
`X-Unsent: 1` を付けてあるので Outlook では未送信の下書きとして開く。

### 意図的に持たせていないもの

- **シェル実行・任意コマンド** — ツールの入力は通知本文（第三者が書いた文字列）の
  影響を受けうる。任意コード実行を与えると、注入がそのまま実行になる。
- **ネットワークアクセス**
- **作業フォルダ外への書き込み** — 絶対パス、`..`、許可外の拡張子は拒否する
  （`.ps1` など実行可能な形式は作れない）。

これらの制限は `phase4/lib/WorkTools.ps1` で強制していて、プロンプトの言い聞かせには
頼っていない。

## 割り込みの受け方

| ユーザーの操作 | ワーカーの反応 |
|---|---|
| 実行中から他の列へドラッグ | `cancel_requested` が立ち、次の区切りで停止。列はユーザーが移した先のまま |
| 「作業を中止」ボタン | 同上 |
| カードにコメント | 次回実行時に未読分を読み、最優先の指示として下書きに反映 |
| 下書き欄を編集 | `user_edited` は上書きされない。次回はそれを土台にする |

中止すると `cancel_requested` とリースは解除されるので、`要対応` に戻せば再開できる。

## 落ちたときの復旧

`agent_lease_until` を過ぎた `実行中` のカードは、次のワーカーが回収して処理し直す。
処理中に例外が出た場合はリースを外して `要対応` に戻し、理由を作業ログに残す。

## 進捗の見せ方

- `task_activity` … カードごとの作業ログ（開始・経過・生成中・完了・エラー・中止）
- `worker_state` … ワーカーの死活と現在の作業（1行のみ）

カンバンのヘッダがワーカーの状態を、カード詳細が作業ログを表示する。
`worker_state` の更新が 90 秒以上止まっていると、UI 側は「エラー（応答なし）」として扱う。

## ハマりどころ

`"=?UTF-8?B?$b64?="` は空文字になる。PowerShell は `?` を変数名の一部として取り込むため、
`$b64?` という未定義変数として解決される。`${b64}` と括ること。
これを踏んだ結果、日本語件名のメールがすべて件名なしで生成されていた。

## 実データでの確認結果

実際の通知から作られたカードに対して実行し、以下を確認した。

- 下書きが生成され、カードが `レビュー待ち` に移動する
- ワーカーが「返信相手が存在しない通知」を認識し、送信文ではなく対応メモの形にした
- 前提と限界（何が判別できなかったか、人間側で必要な操作）を `notes` に列挙し、
  カードのコメントとして残した

つまり、通知単体では文脈が足りないという Phase 1 の結論は下書きの質にも表れている。
Slack / メールの本文を正規 API で取得できれば、ここが改善する見込み。
