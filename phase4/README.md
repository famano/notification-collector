# Phase 4 — ワーカー

`要対応` のカードを拾って下書きを作り、`レビュー待ち` に置く。

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\phase4\Start-Worker.ps1
```

`-Once` で1周だけ実行。Claude の API キーが要る（環境変数 `ANTHROPIC_API_KEY`、
カンバンの「接続」から入れたもの、配布設定のいずれか。`lib\ApiKey.ps1` が順に見る）。

## 何をきっかけに動くのか

**イベント駆動ではなく、常駐プロセスのポーリング**です。カードを作ったり動かしたりしても
通知は飛びません。5秒ごとに DB を見て、拾えるカードがあれば処理します。

**ワーカーを起動していない限り、何をしても動きません。** カンバンは別プロセスなので、
ボードを開いているだけでは作業は進みません。

**逆に、ワーカーはカードを作りません。** 見ているのは `tasks` テーブルだけで、
Gmail も Outlook も Slack も Teams も Chatwork も Backlog も通知 DB も読みません。新しいメールがカードになるには
`Start-Collector.ps1` (取り込みとトリアージ) が別に常駐している必要があります。
ワーカーとカンバンだけを起動して待っても、「要対応」は永久に空のままです。

拾う条件（[`Get-NextWorkItem`](../phase2/lib/TaskStore.ps1)）:

| 条件 | 内容 |
|---|---|
| 列 | `要対応`、または**リースが切れた** `実行中`（落ちたワーカーの後始末） |
| 中止要求 | `cancel_requested = 0` であること |
| アーカイブ | されていないこと |
| 順序 | 緊急度（高→中→低）、次に ID の昇順 |

つまり以下は**動きません**:

- `未分類` `レビュー待ち` `完了` `対応不要` にあるカード
- 中止要求が残っているカード（`要対応` にあっても飛ばされる）
- 既存カードの本文を編集しただけ（再実行はされない）

もう一度やらせたい場合は、カードを `要対応` にドラッグしてください。
このとき中止要求は自動で解除されます。

## 失敗の扱い

例外が出たカードはリースを外して `要対応` に戻します。ただし**同じカードで3回続けて
失敗したら棚上げ**し（中止要求を立てて対象外にする）、理由を作業ログに残します。
残高不足やキー不正のような恒久的な失敗で、同じカードを永久に拾い直し続けるのを
防ぐためです。原因を解消したあと「中止を解除して要対応へ」で再開できます。

失敗直後は30秒待ってから次に進みます（API 側の問題を叩き続けないため）。

## 1枚のカードを処理する流れ

```
要対応 → [リース取得] → 実行中 → 未読の指示を読む
                                    ↓
              Claude がツールを使って成果物を作る（複数ターン）
                 危険なツールは承認待ちで停止 ──→ 利用者が許可/拒否
                                    ↓
                        自己検証（別の会話）
                          ├ 問題なし ──────────┐
                          └ 要修正 → 指摘を戻して修正 → 再検証
                                    ↓
                       報告を agent_output に保存 → レビュー待ち
```

**ツールを実行する直前ごと**に中止要求を確認する。生成が終わった直後にも確認し、
途中でユーザーが中止していれば結果を捨てる。承認待ちは `-ApprovalTimeoutSec`
（既定600秒）で、超えたら実行しない。自己検証で要修正になったときは、
新しい会話ではなく**同じ会話の続き**で指摘を渡して直させる。

### ツールの回数の上限

1回の作業でツールを使えるのは `policy.json` の `worker.maxTurns` 回まで（既定 40。
`-MaxTurns` で上書きできる）。以前は 12 で、CI の失敗を調べるだけ
（runs → jobs → 注釈 → ログ → コミット → ファイル）で使い切っていた。

**上限に達しても例外にしない。** 以前は例外にして `要対応` に戻し、最初からやり直していた。
その間に外へ出したもの（#295 では PR へのコメント）だけが残り、2回目は同じ調査を
急いでなぞって、確かめないまま PUT を打った。いまは最後に1回だけツールを外して
（`tool_choice: none`）ここまでの報告を書かせ、先頭に【途中で止まっています】を付けて
`レビュー待ち` に置く。続けるなら差し戻せば、同じ会話の続きから再開する。

出力の上限（`worker.maxOutputTokens`、既定 16000）は判定とは別に持つ。thinking と
共用なので、判定と同じ 4096 では長い本文を書く途中で切れる。**上限で切れた応答の
ツール呼び出しは実行しない** ―― 入力の JSON が途中で閉じられていて、中身は書こうと
したものの一部でしかない（長い本文を送る PUT なら、ファイルの頭だけで全体を置き換える）。

### やり直しは会話の続きから

モデルとの会話はカードごとに `task_sessions` に残す（ツールを1回使うごとに保存）。
差し戻し・上限での停止・自己検証の直し・落ちた実行の回収は、どれも**前回の会話の続き**として
進める。以前は毎回会話を捨てていたので、差し戻すと最初から調べ直し、自分が前回
何をしたかを知らないまま作業していた ―― #295 では「テストファイルを空にしたのは
きみか」と聞かれて「GET しか出していない」と答えた。

続きから始めるときは末尾に「再開」の依頼を足す。過去の発言は書き換えない
（thinking ブロックは無改変で返す必要があり、書き換えは API に検出される）。

| 足すもの | なぜ |
|---|---|
| 前回からの経過時間と「書く前に今の状態を読んで確かめて」 | 間に外の状態が変わる。#295 では壊したファイルを利用者が手で直していた |
| 元のやり取りを取り直して変わっていれば、その全文 | 相手が返信していることがある |
| 前回の点検で残った指摘 | 点検役は別の会話なので、ワーカーの会話には無い |
| 利用者の新しい指示 | 最優先 |

**結果の残っていないツール呼び出しは再実行しない。** 途中で落ちた実行の跡で、
実行されたかどうかは分からない。「分からないので確かめてから進めて」を結果として返す。
書き込みや送信をもう一度流すより安全。

**続きからにできないとき**は、会話を捨てて、記録から組み立てた「前回までの経過」を
新しい会話に渡す。経過はモデルに要約させない ―― モデルの書く経過は自分に都合よく欠ける
（上の「GET しか出していない」がそれ）。実際に何を叩いて何が返ったか（`task_attempts`）、
前回の報告、点検で残った指摘から組み立てる。

| 続きからにしない | 理由 |
|---|---|
| 同じ件の新しい発生（次の CI の失敗など） | 別の出来事 |
| 前回呼んだツールが今の一覧に無い | 宙に浮いた呼び出しを抱えた会話は API に弾かれる |
| 会話が長すぎる（`-MaxSessionChars`、既定 200 万字） | |
| 会話を残す前に作業したカード | 以前の版で作業したもの |
| 利用者が「最初からやり直す」を選んだ | 間違った思い込みごと続いてしまうとき。差し戻す欄にある |

### 古いツール結果は消す（要約しない）

会話が伸びると、古いツール結果（API の応答）が大半を占める。これは API の
context editing（`clear_tool_uses`）で消す。入力が `worker.clearTrigger`（既定 8 万
トークン）を超えたら、直近 `worker.clearKeep` 回ぶん（既定 8）を残して古いものを消す。
消すたびにキャッシュが壊れるので、2 万トークン以上まとめて消せるときだけ消す。

要約（compaction）は使わない。SWE-bench での比較では、古い観測を隠すだけの方式が
LLM による要約と同等以上の解決率で、費用はおよそ半分だった。要約を重ねるほど細部が
落ちるのは Claude Code・Codex CLI に共通の失敗でもある。消えて困るもの
（何を書き込んだか・利用者の指示・点検の指摘）は会話ではなく DB から毎回渡す。
API に context editing を断られたら、そのプロセスでは以後付けずに続ける。

## 実際にできる作業

説明を書くのではなく、ツールで**実際に用事を終わらせる**。
ツールは「カードの出口」で3つに分かれている。

**見る** ―― 出自を取り直す。承認不要。

| ツール | 内容 |
|---|---|
| `open_source` | 元のメール (Gmail / Outlook) / Slack スレッド / Teams・Chatwork の会話 / Backlog の課題 / Claude セッションを取り直して全文を読む |
| `fetch_attachment` | 添付を取り込む（やるべきことが添付にしか無いことがある）。名前を省くと元の名前で保存し、テキストなら中身も返す |
| `recall` | 同じ件について前回までに分かったことを読む |
| `record_finding` | 次回も効く事実を台帳に残す |

`open_source` は**ワーカーが作業開始前に自動で呼び、結果を依頼と一緒に渡す。**
モデルへの指示に頼った形では守られず、本文の後半を読まないまま報告が出た。

**効かせる** ―― 相手の状態を変える。

| ツール | 承認 | 内容 |
|---|---|---|
| `http_request` | GET は自動/その他は**必要** | 任意の HTTP。招待の承諾、出欠の返信など |
| `run_command` | **必要** | PowerShell コマンドの実行 |
| `write_file` / `read_file` / `list_files` | 場合による | ファイル操作 |

**閉じる**

| ツール | 承認 | 内容 |
|---|---|---|
| `propose_reply` | 不要 | 返信文面をカンバンの「送る」欄に載せる（返信先があるカードのみ） |
| `require_human_step` | 不要 | 本人にしかできない1手を提示して閉じる（後述の条件あり） |
| `create_email_draft` | 不要 | メールの下書きを `.eml` として作成 |
| `create_gmail_draft` | **必要** | Gmail に本物の下書きを作成（Gmail 連携時のみ） |
| `send_gmail` | **必要** | メールの送信（Gmail 連携時のみ） |
| `create_outlook_draft` | **必要** | Outlook に本物の下書きを作成（Microsoft 365 連携時のみ） |
| `send_outlook_mail` | **必要** | Outlook からメールの送信（Microsoft 365 連携時のみ） |
| `send_slack_message` | **必要** | 元の Slack スレッドへの投稿（Slack 由来のカードのみ） |
| `send_teams_message` | **必要** | 元の Teams のチャットへの投稿（Teams 由来のカードのみ） |
| `send_chatwork_message` | **必要** | 元の Chatwork の部屋への投稿（Chatwork 由来のカードのみ） |
| `add_backlog_comment` | **必要** | 元の Backlog の課題へのコメント（Backlog 由来のカードのみ） |

成果物は `phase4/output/task-NNNN/` に出る。カード詳細に一覧が出て中身も確認できる。
ただし**メモを作ることは成果ではない。** 求められていないファイルを作って
報告するのは、カードが閉じていないということなので、自己検証で指摘される。

### http_request の危険度は「メソッド × ホスト」で決まる

ツール名ではなく、何をどこへ投げるかで決める。

| | 資格情報が付く既知ホスト | それ以外 |
|---|---|---|
| GET / HEAD | 自動（同期の読み取りと同じ） | **承認**（URL に情報が載りうる） |
| POST / PATCH / PUT / DELETE | **承認** | **承認** |

書き込みメソッドは送信と同じ「取り消せないもの」として扱う。
一度通ったら修正ラウンドで投げ直さない。

### 書き込みは「足す」と「上書き・消す」を分ける

| 種類 | メソッド | まとめて許可 |
|---|---|---|
| 読む | GET / HEAD | 資格情報の付かないホストだけ承認。許可はホストごと |
| 足す | POST | できる（コメント・予定・下書き。取り消しても害が小さい） |
| 上書き・消す | PUT / PATCH / DELETE | **書く前に突き合わせられたものだけ** |

許可は**ツール名ではなく「種類 × ホスト」**で持つ（`http_request:add:api.github.com`）。
以前はツール名で束ねていたので、9/13 に GET を通すつもりで押した「今後すべて許可」が、
#295 で GitHub への PUT まで無承認にしていた。以前の `http_request` の許可は、
起動時に**読み取りだけの許可**（`http_request:read:*`）に置き換わる。

**上書き・消すの前には、同じ URL を GET して突き合わせる**（`lib\WritePreview.ps1`）。
特定のサービスの知識は使わない。送る本文といまの状態の、両方にあるフィールドを比べ、
base64 の値はデコードしてから長さと中身を比べる。

| 突き合わせ | 扱い |
|---|---|
| 小さな変更 | 許可があれば自動 |
| いまは無い (GET が 404) | 新規作成。許可があれば自動 |
| 半分以下に減る / DELETE | **実行せずに差分をモデルに返す**。意図どおりなら `confirm_large_change` で呼び直させ、そのうえで**許可や自動承認があっても承認画面で止める** |
| 形が違って比べられない / 読めない | 承認画面に「影響を事前に確認できません」。まとめて許可は出さない |

#295 の PUT（10,361 → 24 バイト）は「実行せずに差分を返す」で止まる。
資格情報の付かない未知のホストは事前に読まない（URL に載った情報を承認の前に出さないため）。

**書いたあとは読み直す。** PUT / PATCH が通ったら同じ URL を GET し、送った値と
一致しているかを結果に添える。書いたつもりのものと実際に入ったものの食い違いに、その場で気付ける。

**base64 は手で書かせない。** ファイルを丸ごと送る API は値を base64 で求めるが、
モデルに手で書かせると出力を食い、1文字の誤りで中身が壊れる（1万字のファイルは 1.4 万字の
base64 になり、以前の出力上限 4096 トークンでは書き切れなかった）。本文は平文で書かせ、
`encode: {"content": "base64"}` で指定したフィールドをワーカーが符号化する。
手で書いた長い base64 は送らずに差し戻す。承認画面にも平文で出す。

**何を書いたかは残す。** 書き込みの本文（平文）と突き合わせ・読み直しの結果は
`task_attempts` の `request` / `preview` に全文残り、カード詳細の「試したこと」で読める。
再開・引き継ぎのときにも、ワーカーはこれで自分が何を書き込んだかを知る。

### 資格情報はモデルに渡らない

`Authorization` は**ワーカーが宛先ホストを見て注入する**。モデルは指定できず、
指定しても捨てられる。結果として:

- モデルはトークンを見られないので、どこかへ書き出せない
- Google のトークンは `googleapis.com` にしか付かない。**未知のホストには何も付かない**
- 承認画面には実際のリクエストが出るが、認証行は `Bearer <Google トークン>` と伏せる
- リクエストに保管中のシークレットが混ざっていたら、承認に出す前に**止める**

**止めるのは秘密だけ。** OAuth のクライアント ID、テナント ID、Backlog のスペース名は
保管庫に入っているが秘密ではなく、URL に載って当たり前の値である。これらまで
「シークレットが混ざっている」で止めると、**1文字も間違っていない呼び出しが通らない** ――
実際、スペース名はホスト名そのものなので、Backlog へのリクエストは全部中止されていた。
検査から外すのは `SecretStore.ps1` の `$NonSecretNames` に挙げたものだけで、
知らない名前は秘密として扱う。

Claude 自身の API も叩ける。版のヘッダ (`anthropic-version`) はワーカーが付ける。
組織全体の口 (`/v1/organizations/...` 利用状況など) だけは**通常のキーでは通らない**ので、
同じホストでも道を見て管理 API キー (任意設定) に切り替える。
**URL に組織 ID は要らない** ―― `organizations` は固定の語で、どの組織を見るかは鍵が決める
(組織 ID を URL に載せる口は Anthropic の API に1つも無い)。

**人に届くメッセージの送信は汎用ツールから叩けない。**
`chat.postMessage`、Gmail の send、Graph の `sendMail`、Chatwork の部屋への POST は
資格情報を注入せず弾く。
ここを通してしまうと「宛先をカードから束縛する」という土台が素通りされる。

Graph だけは**メソッドまで見る。**`/chats/{id}/messages` は POST が投稿で
GET が閲覧という、**読むのと送るので同じ URL** の API だからで、
URL だけで塞ぐとチャットの本文が取れなくなる。

### 「本人にしかできない1手」で閉じる

生体認証・本人確認リンク・支払いは、原理的にソフトウェアには出来ない。
`require_human_step` はそれを**失敗ではなく正式な出口**として扱い、
1手とリンクと期限だけをカードの表に出す。

ただし手を尽くす前には呼べない。`task_attempts` に残った実際の実行記録で判定する。

| blocker | 通す条件 | 扱い |
|---|---|---|
| `credential_missing` | 実際に叩いて断られた記録が要る | **カードを閉じず、設定カードを立てる** |
| `no_api` | 実際に試した記録が要る | 本人の1手として閉じる |
| `physical_presence` | 出自を読んでいれば通す | 本人の1手として閉じる |
| `payment_or_legal` | 出自を読んでいれば通す | 本人の1手として閉じる |
| `beyond_tools` | 出自を読んでいれば通す（**試した証跡は求めない**） | 引き渡しとして閉じる |

### 道具が足りないときは、引き渡す

`beyond_tools` は「手段はあるが、手持ちの道具では正しく・結果を確かめながらできない」作業の出口。
リポジトリのコードやテストを直す（差分の適用・テストの実行・レビューが要る）、画面操作が要る、など。

#295 では、CI の失敗を直そうとしたこと自体は正しかったが、ワーカーの道具は `http_request` だけで、
ファイル編集を PUT contents と git trees で組み立てて、テストファイル全体を1行にした。
道具が足りないときに正しく引き下がる道が無く、しかもプロンプトは「手を尽くせ」
「状態を変える操作を過度に恐れるな」と一方向にだけ押していた。

- **引き下がることを罰しない。** 他の blocker と違い、`http_request` で試した証跡を求めない ――
  試すこと自体（HTTP でファイル編集を組み立てる）が壊す原因になる。step には
  「何をどう直せばよいか」をそのまま作業に取りかかれる具体さで書かせる
- **下位の道具で別の作業を再現させない。** システムプロンプトで、http_request でファイル編集や
  git の操作を組み立てないこと、頼まれていない書き込みをしないことを明示した
- **「承認があるから大丈夫」と言わない。** 以前のプロンプトは「GET 以外は承認画面に全文が出るので、
  過度に恐れる必要はない」と書いていたが、許可済みなら承認画面は出ない。いまは
  「許可によっては承認なしで実行される。結果を自分で確かめられる操作だけを行え」と書いてある
- **点検は両方向に見る。** 検証役は「手を尽くさずに投げ返した」を重く見ていたが、やりすぎを見る
  基準が無かった。依頼の範囲を超えた書き込み・確かめられない方法での書き込み・書いた結果の
  大きな減少を `high` にし、`beyond_tools` での引き渡しは欠陥として扱わない

差し戻されたときは理由がモデルに返るので、別の手を試せる。
何を試して何が返ったかはカード詳細の「試したこと」に出る ――
「できませんでした」が手を尽くした結果なのか諦めなのかを、
報告の書きぶりではなくここで確かめられる。

### 名義 ―― 誰の代わりに書いているか

外に出る文面は、すべて利用者本人のアカウントから本人の発言として出る。
ところが以前は、モデルに渡していたのがスレッド全文だけだった。誰の代わりに
書いているかはどこにも書いておらず、**本文の中で一番「返事をする人」に見えるのは
To: の人**なので、To: 他人 / Cc: 自分 で届いたメールでは、その他人の名義で
返信を下書きしていた (読み手からは「本人が他人のふりをして返してきた」に見える)。

投稿先を束縛するのと同じで、これも指示ではなく構造で担保する。
ワーカーは1枚の処理に入る手前で「このカードでのあなた」を決め、プロンプトに渡す。

| | どこから決まるか |
|---|---|
| 名義 | **カードが届いたアカウント**の名前 (`account.<連携先>`、疎通確認のときに保存したもの)。返信もここから出る |
| 立場 | 取り直した出自のヘッダ。`From` / `To` / `Cc` を、**繋いである全アカウント**のアドレスと突き合わせる |

**名義は1つだが、本人は1人。**仕事用と個人用の Gmail を両方繋いでいると、片方宛の
メールがもう片方の受信箱にも届く (両方が宛先、転送、メーリングリスト)。立場を
カードのアカウントのアドレスだけで見ると、**本人宛のメールを「宛先は他人」と読む** ――
症状は「自分宛なのに横で見ているだけの扱いになり、返さなくなる」で、静かに効く。
別のアカウントのアドレスで当たった場合は、そのことも渡す
(本人宛だが、返信はこのカードのアカウントから出るため)。

立場で既定の振る舞いが変わる。

| 立場 | 既定 |
|---|---|
| 宛先 (To) | 本人の名義で返信する |
| Cc | **返信しない。** 返事を求められているのは本人ではない。状況を報告に書いて閉じる。伝えるべきことがあるときだけ、本人の名義で横から短く差し込む |
| 送信者 (From) | 自分が出したメールの続き。必要なら本人の名義で追いかける |
| 宛先に本人が無い | Cc と同じ扱い (メーリングリスト・転送) |
| 不明 | 立場を断定させない。名義の束縛だけは効く |

ヘッダが引けなかったときに立場を当て推量しない ――「Cc のはず」と決めて
返信を止めるほうが、分からないと言うより害が大きい。
自己検証も名義を見て、他人になりきって書いていれば `high` で差し戻す。
承認画面にも差出人 (名義) が出るので、通る前に人の目でも止められる。

### 送信を指示されていないときは、文面をカードに載せる

返信先があるカードで利用者が送信を指示していない場合、`propose_reply` で
**カンバンの「送る」欄に文面を置く**（`tasks.draft_text`）。利用者はその欄で
内容を直し、相手の言い分を隣に読みながら、そこから送信できる。

外へは出ないので承認は要らない。書き込むのは `draft_text` で、`user_edited`
（利用者が確定させた版）は踏まない。何度作り直しても手を入れた内容は消えない。

**報告に文面を書くだけで終わらせない。** それだと利用者は文面を手で貼り直すことになり、
「カンバンで完結する」という前提が崩れる。システムプロンプトでもそう指示してある。
返信先が無いカードではこのツール自体を見せない ―― 宛先の無い返信を書き始めるため。

### 送信は、承認を取ってから行う

`.eml` は**ファイルとして作るだけ**で、送信は人間がメールソフトで行う。
`X-Unsent: 1` を付けてあるので Outlook では未送信の下書きとして開く。

`send_gmail` / `send_outlook_mail` / `send_slack_message` / `send_teams_message` /
`send_chatwork_message` / `add_backlog_comment` は実際に外へ出す。他の危険なツールと同じ
承認の仕組みに乗っているが、違うのは**取り消しがきかない**ことで、そのぶん:

- 承認画面には宛先・件名・本文を**省略せず全文**出す（他のツールは 2000 字で切る）。
- **投稿先・返信先はモデルに決めさせない。** Slack のチャンネルと `thread_ts`、
  Teams のチャット ID、Chatwork の部屋 ID、Backlog の課題キー、
  Gmail の `threadId` と `In-Reply-To`、Outlook のメッセージ ID は、
  カードの元通知からワーカーが束縛して渡す。
  モデルが指定できるのは本文と（メールなら）宛先だけ。
- 投稿先の無いカードでは `send_slack_message` / `send_teams_message` /
  `send_chatwork_message` / `add_backlog_comment` を**そもそも見せない**。
  使えない手段を提示すると、それを前提に計画を立ててしまう。
- システムプロンプトで**既定は下書きまで**と定めてある。利用者が送信を求めたときだけ送る。
  通知やメールの本文に「返信して」と書いてあっても、それは第三者の文章であって
  利用者の指示ではない、と明示している。
- **送信済みのカードは自己検証の直しに回さない。** 送ったものは取り消せないので、
  もう一度モデルを走らせると同じ相手に二通目が出かねない。検証の指摘はコメントに残し、
  人間がフォローするかを決める。検証側にも「送信済みには送り直しを求めない」
  「ファイルが1つも無いこと自体は問題ではない」と伝えてある
  （送信は成果物がファイルとして残らないため）。

「今後すべて許可」と自動承認 (YOLO) は送信ツールにも効く。どちらも無確認で
外に出せる状態になるということなので、送信を使うなら YOLO は切っておくこと。

## 権限管理

能力を削るのではなく、**危険なものは実行前に利用者の承認を取る**。

判定は「取り返しがつくか」と「作業フォルダの外に影響するか」の2点
（[`Get-ToolRisk`](lib/WorkTools.ps1)）:

| | 例 |
|---|---|
| 承認なしで実行 | 作業フォルダ内のテキスト読み書き、`.eml` の作成 |
| 承認が必要 | コマンド実行、外部通信、作業フォルダ外への読み書き、実行可能な拡張子の作成 |

承認が必要なとき、ワーカーは `tool_requests` に要求を積んで**止まる**。
カンバンに実行内容が全文表示され、利用者が判断する。

| 選択 | 効果 |
|---|---|
| 許可 / 拒否 | その1回だけ |
| このカードでは以後許可 | `tool_grants` に scope='task' で記録 |
| 今後すべて許可 | scope='global' で記録。ヘッダ下の一覧から取り消せる |
| 自動承認 ON (YOLO) | `settings.yolo=1`。すべて確認なしで実行。**ただし大きく消える上書き・削除は止まる** |

束ねる単位は承認要求に記録した鍵（http_request は「種類 × ホスト」）で、画面からは受け取らない。
影響を事前に確かめられない上書き・大きく消える上書きの承認画面には、「まとめて許可」を出さない。

### 外に出したあとで問題が見つかったら、赤く出し続ける

送信済みのカードは自己検証の直しに回さない（二通目が出かねない）。ただし
「人間の確認に回す」を、ほかのカードと同じ見た目のレビュー待ちで済ませていた。
#295 では点検が「テストファイルを1行にして壊した」と正しく見つけていたのに、
利用者はリポジトリがおかしくなってから気付いた。

いまは、書き込み・送信のあとで点検が `high` を出したら `tasks.alert` に印を付ける。
カードの表とカード詳細の先頭（報告より上）に赤で出し、残った指摘をそのまま見せる。
利用者が「確認した」を押すまで消えない。

### 送ったものは作業ログに残る

`task_activity` に `sent` 種別で1行入り、カンバンの作業ログでは赤字で出る。
カードの報告 (`agent_output`) にも「送信済み (n 件)」として並ぶ。
成果物のファイルと違って後から中身を確かめる手段が無いので、
**承認画面が唯一の事前確認、作業ログが唯一の事後記録**になる。

### 起動時に連携状況を出す

ライブラリは起動時にしか読み込まない。コードを更新しても、動いたままのワーカーは
古いツール一覧のままになる。起動直後に出る

```
連携: Gmail=有効 (下書き・送信) / Slack=有効 (Slack 由来のカードに投稿) / Microsoft365=有効 (…) / Chatwork=有効 (…) / Backlog=有効 (…)
```

を見れば、いま動いているプロセスが送信できる版かどうかが分かる。
この行が出ない、または `無効` なら、送信ツールはモデルに渡っていない。

**拒否は例外にしない。** 「利用者が許可しませんでした」という結果をモデルに返すので、
別の手段を検討するか、できない旨を報告に書く。実測では、コマンド実行を拒否したとき
「手順書と空の表」を作って未取得の理由を明記した。

### 承認画面で気をつけること

承認画面は実行内容を省略せずに出す。ここが**注入と実行のあいだに立つ唯一の壁**になる。
通知やメールの本文はワーカーの入力に混ざるため、そこに書かれた指示が
コマンドや URL の形で承認画面に現れうる。コマンド本文と URL は必ず読むこと。

`http_request` は GET でも、URL のクエリに情報を載せれば外部に出せる。
承認画面に URL 全体を出しているのはそのため。書き込みメソッドでは本文も全文出る。
認証情報だけは伏せ字にする ―― モデルは元々持っていないので、
ここに実トークンを出しても確認の役に立たず、画面から漏れる面だけが増える。

YOLO を有効にすると、この壁は無くなる。有効化時に確認ダイアログを出している。

## 覚えておくことを整理する

手が空いたとき、ワーカーは**閉じたカードから「次に似た件が来たときにも効くこと」**を
1枚ずつ拾う (`-NoMemory` で止められる。遡る幅は `-MemoryLookbackDays`、既定 30 日)。

- 材料は利用者が書いたもの (差し戻しの指示・完了時の記録) と、**実際に試したことの記録**。
  何を叩いて何が返ったかは次の件にそのまま効く。ただし自分の言い分
  (なぜそうしたか、なぜできなかったか) は覚えない ―― 事実だけを取る
- **閉じたあとに行う。** 完了メモはカードを閉じるときに書かれるので、
  作業の直後に覚えると一番はっきりした材料 (「次からはこうして」) を必ず取りこぼす
- **待機中にだけ行う。** 人が待っているのは目の前の1枚であって、記憶の整理ではない
- 覚えることが無ければ空で返してよい。無理に絞り出させない
- 失敗したら印を付けずに間を置く。材料はカードに残っているので、直ったあとに拾い直せる

覚えたものは次からの判定と作業に渡る。カードの文面では選り分けず、
覚えていること全部を渡す (量は保存する側の上限で抑える)。詳しくは
[phase2/README.md](../phase2/README.md#利用者について覚えておく)。

## 自己検証

作業が終わったあと、**別の会話**で成果物を点検する。作った本人の前提を引き継がせないため、
検証エージェントには依頼と成果物だけを渡す。

見るのは、依頼が満たされているか / 途中で終わっていないか / プレースホルダや
未説明の空欄が残っていないか / 依頼にない事実を作っていないか / 報告と中身が食い違わないか。

`needs_fix` なら指摘をワーカーに戻して直させ、再度検証する（`-MaxRepairs`、既定1回）。
解消しなければ打ち切り、残った指摘をカードに残す（`task_comments` の `kind='verify'`）。
`-NoVerify` で無効にできる。

**検証の結果は報告に書かない。** 以前は末尾に `[自己検証: 問題なし] …` を付けていたが、
利用者が読んでも判断は変わらない（問題なしなら読み飛ばし、要確認なら要るのは指摘そのもの）。
結果は作業ログに、残った指摘はカード詳細の「自己検証の指摘」に畳んで出す。
次にそのカードを作業するとき（再開・引き継ぎ）にはワーカーにも渡る。

**報告の宛先は利用者。** 直しの回に指摘をそのまま渡すと、最後の文章が
「ご指摘の点を修正しました」という点検役への返事になり、それが報告として利用者に届いていた。
直しは同じ会話の続きとして渡し、「利用者にはこの指摘は見えていない。最終的に何をしたかを
最初から読める形で書け」と添える。システムプロンプトにも同じことを書いてある。

## 報告はやりとりに積む

報告は `agent_output` に入り、カード詳細の先頭に出る。ただしここは最新の1件で上書きされるので、
差し戻して作業させるたびに前回の報告が読めなくなっていた。いまは作業のたびに報告を
やりとり（`task_comments` の `kind='report'`）にも1件ずつ積む。やりとりには利用者の指示と
ワーカーの報告だけが交互に並び、経緯として読み返せる。

検証エージェントは、`TODO` のまま・本文の途中切れ・説明のない空欄・
報告と実物の食い違いを実測で検出できている。

## 割り込みの受け方

| ユーザーの操作 | ワーカーの反応 |
|---|---|
| 実行中から他の列へドラッグ | `cancel_requested` が立ち、次の区切りで停止。列はユーザーが移した先のまま |
| 「作業を中止」ボタン | 同上 |
| カードにコメント | 次回実行時に未読分を読み、最優先の指示として、前回の会話の続きで反映 |
| 下書き欄を編集 | `user_edited` は上書きされない。次回はそれを土台にする |

中止すると `cancel_requested` とリースは解除されるので、`要対応` に戻せば再開できる。

## 落ちたときの復旧

`agent_lease_until` を過ぎた `実行中` のカードは、次のワーカーが回収して、
残っている会話の続きから処理する（結果の残っていないツール呼び出しは再実行しない）。
処理中に例外が出た場合はリースを外して `要対応` に戻し、理由を作業ログに残す。

## 進捗の見せ方

- `task_activity` … カードごとの作業ログ（開始・経過・生成中・完了・エラー・中止）
- `worker_state` … ワーカーの死活と現在の作業（1行のみ）

カンバンのヘッダがワーカーの状態を、カード詳細が作業ログを表示する。
`worker_state` の更新が 90 秒以上止まっていると、UI 側は「エラー（応答なし）」として扱う。

## ハマりどころ

`"=?UTF-8?B?$b64?="` は空文字になる。PowerShell は `?` を変数名の一部として取り込むため、
`$b64?` という未定義変数として解決される。`${b64}` と括ること。
これを踏んだ結果、日本語件名のメールがすべて件名なしで生成されていた。

## 権限と検証の確認結果

隔離したDBで一連の流れを実測した。

**承認して実行:** 「ディスク使用状況レポート」を依頼 → ワーカーが `run_command` を要求して停止
→ カンバンに実行するコマンドが全文表示される → 許可 → 実行 → `report.md` を作成
→ 自己検証「問題なし」 → レビュー待ちへ。レポートの数値は `Get-PSDrive` の実測値と一致した。

**拒否したとき:** 「インストール済みソフト一覧」を依頼 → コマンド実行を拒否
→ ワーカーは手順書と空の表を作り、未取得の理由を明記
→ 検証が「依頼の核心が未達」と指摘 → 修正を試みる → 再度拒否
→ 1回の上限で打ち切り、`[自己検証: 要確認]` を付けて残った指摘をコメントに記録。

**検証エージェント単体:** `TODO` のまま・「ここに記載」・本文の途中切れ・説明のない空欄・
報告と実物の食い違いを、いずれも `severity=high` として検出した。

## 実データでの確認結果

実際の通知から作られたカードに対して実行し、以下を確認した。

- 下書きが生成され、カードが `レビュー待ち` に移動する
- ワーカーが「返信相手が存在しない通知」を認識し、送信文ではなく対応メモの形にした
- 前提と限界（何が判別できなかったか、人間側で必要な操作）を `notes` に列挙し、
  カードのコメントとして残した

つまり、通知単体では文脈が足りないという Phase 1 の結論は下書きの質にも表れている。
Slack / メールの本文を正規 API で取得できれば、ここが改善する見込み。

## Claude Code への引き渡し

`beyond_tools` で引き渡されたカードのうち、GitHub のリポジトリのコード修正（`repo` に
`owner/name` が書かれたもの）は、カードを開くと「Claude Code に渡す」が出る。

ワーカーにファイル編集の道具を足していくのは、Claude Code の作り直しになる
（差分の適用・テストの実行・書いたものの確認）。ワーカーは引き渡すところまでにして、
その先を手元の Claude Code（`claude -p`）に任せる。

| 段 | 何をするか |
|---|---|
| 押す前 | 渡す文面を全文見せる。文面はワーカーが第三者の文面（通知・CI のログ）から組み立てたもの |
| 手元の clone | 初回だけフォルダを入れる。**origin がそのリポジトリを指していなければ断る**（画面から来たパスを信じない）。以後は覚える |
| 作業場所 | `%LOCALAPPDATA%\notification-collector\worktrees\task-NNNN` に、新しいブランチ `nc/task-NNNN` の worktree を切る。利用者の作業ツリーにも既存のブランチにも触らない |
| Claude Code | `claude -p --output-format json --permission-mode acceptEdits`。`git push`・`gh`・ブランチの切り替え・WebFetch・WebSearch は止める。費用の上限 `delegation.maxBudgetUsd`（既定 5 ドル）、`delegation.timeoutMinutes`（既定 30 分）で止める |
| push と PR | コミットがあれば、**このスクリプトが新しいブランチだけを push し、下書きの PR にする**（GitHub トークンがあれば）。マージは人が決める ―― 壊れるとしても PR の中まで |
| 結果 | やりとりに報告として残し、PR のリンクを出す。カードはレビュー待ちのまま |

**Windows ではコマンドからの通信は止められない。** Claude Code のサンドボックスは
macOS / Linux / WSL2 だけで、Bash（テストの実行に要る）を許すと、そこからの通信は制限できない。
押す前の画面にもそう書いてある。渡す文面を読んでから押すこと。

実行の本体は `Start-Delegation.ps1`（カンバンが別プロセスで起動し、ログは `logs\delegation-NNN.log`）。
