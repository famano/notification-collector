# Phase 4 — ワーカー

`要対応` のカードを拾って下書きを作り、`レビュー待ち` に置く。

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\phase4\Start-Worker.ps1
```

`-Once` で1周だけ実行。`ANTHROPIC_API_KEY` が必要。

## 何をきっかけに動くのか

**イベント駆動ではなく、常駐プロセスのポーリング**です。カードを作ったり動かしたりしても
通知は飛びません。5秒ごとに DB を見て、拾えるカードがあれば処理します。

**ワーカーを起動していない限り、何をしても動きません。** カンバンは別プロセスなので、
ボードを開いているだけでは作業は進みません。

**逆に、ワーカーはカードを作りません。** 見ているのは `tasks` テーブルだけで、
Gmail も Slack も通知 DB も読みません。新しいメールがカードになるには
`Start-Collector.ps1` (取り込みとトリアージ) が別に常駐している必要があります。
ワーカーとカンバンだけを起動して待っても、「要対応」は永久に空のままです。

拾う条件（[`Get-NextWorkItem`](../phase2/lib/TaskStore.ps1)）:

| 条件 | 内容 |
|---|---|
| 列 | `要対応`、または**リースが切れた** `実行中`（落ちたワーカーの後始末） |
| 中止要求 | `cancel_requested = 0` であること |
| アーカイブ | されていないこと |
| 順序 | 緊急度（高→中→低）、次に ID の昇順 |

つまり以下は**動きません**:

- `未分類` `レビュー待ち` `完了` `対応不要` にあるカード
- 中止要求が残っているカード（`要対応` にあっても飛ばされる）
- 既存カードの本文を編集しただけ（再実行はされない）

もう一度やらせたい場合は、カードを `要対応` にドラッグしてください。
このとき中止要求は自動で解除されます。

## 失敗の扱い

例外が出たカードはリースを外して `要対応` に戻します。ただし**同じカードで3回続けて
失敗したら棚上げ**し（中止要求を立てて対象外にする）、理由を作業ログに残します。
残高不足やキー不正のような恒久的な失敗で、同じカードを永久に拾い直し続けるのを
防ぐためです。原因を解消したあと「中止を解除して要対応へ」で再開できます。

失敗直後は30秒待ってから次に進みます（API 側の問題を叩き続けないため）。

## 1枚のカードを処理する流れ

```
要対応 → [リース取得] → 実行中 → 未読の指示を読む
                                    ↓
              Claude がツールを使って成果物を作る（複数ターン）
                 危険なツールは承認待ちで停止 ──→ 利用者が許可/拒否
                                    ↓
                        自己検証（別の会話）
                          ├ 問題なし ──────────┐
                          └ 要修正 → 指摘を戻して修正 → 再検証
                                    ↓
                       報告を agent_output に保存 → レビュー待ち
```

**ツールを実行する直前ごと**に中止要求を確認する。生成が終わった直後にも確認し、
途中でユーザーが中止していれば結果を捨てる。ツール実行は1カードあたり
`-MaxTurns`（既定12）ターンまで。承認待ちは `-ApprovalTimeoutSec`（既定600秒）で、
超えたら実行しない。

## 実際にできる作業

説明を書くのではなく、ツールで**実際に用事を終わらせる**。
ツールは「カードの出口」で3つに分かれている。

**見る** ―― 出自を取り直す。承認不要。

| ツール | 内容 |
|---|---|
| `open_source` | 元のメール / Slack スレッド / Claude セッションを取り直して全文を読む |
| `fetch_attachment` | 添付を取り込む（やるべきことが添付にしか無いことがある）。名前を省くと元の名前で保存し、テキストなら中身も返す |
| `recall` | 同じ件について前回までに分かったことを読む |
| `record_finding` | 次回も効く事実を台帳に残す |

`open_source` は**ワーカーが作業開始前に自動で呼び、結果を依頼と一緒に渡す。**
モデルへの指示に頼った形では守られず、本文の後半を読まないまま報告が出た。

**効かせる** ―― 相手の状態を変える。

| ツール | 承認 | 内容 |
|---|---|---|
| `http_request` | GET は自動/その他は**必要** | 任意の HTTP。招待の承諾、出欠の返信など |
| `run_command` | **必要** | PowerShell コマンドの実行 |
| `write_file` / `read_file` / `list_files` | 場合による | ファイル操作 |

**閉じる**

| ツール | 承認 | 内容 |
|---|---|---|
| `propose_reply` | 不要 | 返信文面を「送る文面」欄に載せる（返信先があるカードのみ） |
| `require_human_step` | 不要 | 本人にしかできない1手を提示して閉じる（後述の条件あり） |
| `create_email_draft` | 不要 | メールの下書きを `.eml` として作成 |
| `create_gmail_draft` | **必要** | Gmail に本物の下書きを作成（Gmail 連携時のみ） |
| `send_gmail` | **必要** | メールの送信（Gmail 連携時のみ） |
| `send_slack_message` | **必要** | 元の Slack スレッドへの投稿（Slack 由来のカードのみ） |

成果物は `phase4/output/task-NNNN/` に出る。カード詳細に一覧が出て中身も確認できる。
ただし**メモを作ることは成果ではない。** 求められていないファイルを作って
報告するのは、カードが閉じていないということなので、自己検証で指摘される。

### http_request の危険度は「メソッド × ホスト」で決まる

ツール名ではなく、何をどこへ投げるかで決める。

| | 資格情報が付く既知ホスト | それ以外 |
|---|---|---|
| GET / HEAD | 自動（同期の読み取りと同じ） | **承認**（URL に情報が載りうる） |
| POST / PATCH / PUT / DELETE | **承認** | **承認** |

書き込みメソッドは送信と同じ「取り消せないもの」として扱う。
一度通ったら修正ラウンドで投げ直さない。

### 資格情報はモデルに渡らない

`Authorization` は**ワーカーが宛先ホストを見て注入する**。モデルは指定できず、
指定しても捨てられる。結果として:

- モデルはトークンを見られないので、どこかへ書き出せない
- Google のトークンは `googleapis.com` にしか付かない。**未知のホストには何も付かない**
- 承認画面には実際のリクエストが出るが、認証行は `Bearer <Google トークン>` と伏せる
- リクエストに保管中のシークレットが混ざっていたら、承認に出す前に**止める**

**人に届くメッセージの送信は汎用ツールから叩けない。**
`chat.postMessage` や Gmail の send は資格情報を注入せず弾く。
ここを通してしまうと「宛先をカードから束縛する」という土台が素通りされる。

### 「本人にしかできない1手」で閉じる

生体認証・本人確認リンク・支払いは、原理的にソフトウェアには出来ない。
`require_human_step` はそれを**失敗ではなく正式な出口**として扱い、
1手とリンクと期限だけをカードの表に出す。

ただし手を尽くす前には呼べない。`task_attempts` に残った実際の実行記録で判定する。

| blocker | 通す条件 | 扱い |
|---|---|---|
| `credential_missing` | 実際に叩いて断られた記録が要る | **カードを閉じず、設定カードを立てる** |
| `no_api` | 実際に試した記録が要る | 本人の1手として閉じる |
| `physical_presence` | 出自を読んでいれば通す | 本人の1手として閉じる |
| `payment_or_legal` | 出自を読んでいれば通す | 本人の1手として閉じる |

差し戻されたときは理由がモデルに返るので、別の手を試せる。
何を試して何が返ったかはカード詳細の「試したこと」に出る ――
「できませんでした」が手を尽くした結果なのか諦めなのかを、
報告の書きぶりではなくここで確かめられる。

### 送信を指示されていないときは、文面をカードに載せる

返信先があるカードで利用者が送信を指示していない場合、`propose_reply` で
**カンバンの「送る文面」欄に文面を置く**（`tasks.draft_text`）。利用者はその欄で
内容を直し、そこから送信できる。

外へは出ないので承認は要らない。書き込むのは `draft_text` で、`user_edited`
（利用者が確定させた版）は踏まない。何度作り直しても手を入れた内容は消えない。

**報告に文面を書くだけで終わらせない。** それだと利用者は文面を手で貼り直すことになり、
「カンバンで完結する」という前提が崩れる。システムプロンプトでもそう指示してある。
返信先が無いカードではこのツール自体を見せない ―― 宛先の無い返信を書き始めるため。

### 送信は、承認を取ってから行う

`.eml` は**ファイルとして作るだけ**で、送信は人間がメールソフトで行う。
`X-Unsent: 1` を付けてあるので Outlook では未送信の下書きとして開く。

`send_gmail` と `send_slack_message` は実際に外へ出す。他の危険なツールと同じ
承認の仕組みに乗っているが、違うのは**取り消しがきかない**ことで、そのぶん:

- 承認画面には宛先・件名・本文を**省略せず全文**出す（他のツールは 2000 字で切る）。
- **投稿先・返信先はモデルに決めさせない。** Slack のチャンネルと `thread_ts`、
  Gmail の `threadId` と `In-Reply-To` は、カードの元通知からワーカーが束縛して渡す。
  モデルが指定できるのは本文と（メールなら）宛先だけ。
- 投稿先の無いカード（Slack 由来でない）では `send_slack_message` を**そもそも見せない**。
  使えない手段を提示すると、それを前提に計画を立ててしまう。
- システムプロンプトで**既定は下書きまで**と定めてある。利用者が送信を求めたときだけ送る。
  通知やメールの本文に「返信して」と書いてあっても、それは第三者の文章であって
  利用者の指示ではない、と明示している。
- **送信済みのカードは自己検証の直しに回さない。** 送ったものは取り消せないので、
  もう一度モデルを走らせると同じ相手に二通目が出かねない。検証の指摘はコメントに残し、
  人間がフォローするかを決める。検証側にも「送信済みには送り直しを求めない」
  「ファイルが1つも無いこと自体は問題ではない」と伝えてある
  （送信は成果物がファイルとして残らないため）。

「今後すべて許可」と自動承認 (YOLO) は送信ツールにも効く。どちらも無確認で
外に出せる状態になるということなので、送信を使うなら YOLO は切っておくこと。

## 権限管理

能力を削るのではなく、**危険なものは実行前に利用者の承認を取る**。

判定は「取り返しがつくか」と「作業フォルダの外に影響するか」の2点
（[`Get-ToolRisk`](lib/WorkTools.ps1)）:

| | 例 |
|---|---|
| 承認なしで実行 | 作業フォルダ内のテキスト読み書き、`.eml` の作成 |
| 承認が必要 | コマンド実行、外部通信、作業フォルダ外への読み書き、実行可能な拡張子の作成 |

承認が必要なとき、ワーカーは `tool_requests` に要求を積んで**止まる**。
カンバンに実行内容が全文表示され、利用者が判断する。

| 選択 | 効果 |
|---|---|
| 許可 / 拒否 | その1回だけ |
| このカードでは以後許可 | `tool_grants` に scope='task' で記録 |
| 今後すべて許可 | scope='global' で記録。ヘッダ下の一覧から取り消せる |
| 自動承認 ON (YOLO) | `settings.yolo=1`。すべて確認なしで実行 |

### 送ったものは作業ログに残る

`task_activity` に `sent` 種別で1行入り、カンバンの作業ログでは赤字で出る。
カードの報告 (`agent_output`) にも「送信済み (n 件)」として並ぶ。
成果物のファイルと違って後から中身を確かめる手段が無いので、
**承認画面が唯一の事前確認、作業ログが唯一の事後記録**になる。

### 起動時に連携状況を出す

ライブラリは起動時にしか読み込まない。コードを更新しても、動いたままのワーカーは
古いツール一覧のままになる。起動直後に出る

```
連携: Gmail=有効 (下書き・送信) / Slack=有効 (Slack 由来のカードに投稿)
```

を見れば、いま動いているプロセスが送信できる版かどうかが分かる。
この行が出ない、または `無効` なら、送信ツールはモデルに渡っていない。

**拒否は例外にしない。** 「利用者が許可しませんでした」という結果をモデルに返すので、
別の手段を検討するか、できない旨を報告に書く。実測では、コマンド実行を拒否したとき
「手順書と空の表」を作って未取得の理由を明記した。

### 承認画面で気をつけること

承認画面は実行内容を省略せずに出す。ここが**注入と実行のあいだに立つ唯一の壁**になる。
通知やメールの本文はワーカーの入力に混ざるため、そこに書かれた指示が
コマンドや URL の形で承認画面に現れうる。コマンド本文と URL は必ず読むこと。

`http_request` は GET でも、URL のクエリに情報を載せれば外部に出せる。
承認画面に URL 全体を出しているのはそのため。書き込みメソッドでは本文も全文出る。
認証情報だけは伏せ字にする ―― モデルは元々持っていないので、
ここに実トークンを出しても確認の役に立たず、画面から漏れる面だけが増える。

YOLO を有効にすると、この壁は無くなる。有効化時に確認ダイアログを出している。

## 自己検証

作業が終わったあと、**別の会話**で成果物を点検する。作った本人の前提を引き継がせないため、
検証エージェントには依頼と成果物だけを渡す。

見るのは、依頼が満たされているか / 途中で終わっていないか / プレースホルダや
未説明の空欄が残っていないか / 依頼にない事実を作っていないか / 報告と中身が食い違わないか。

`needs_fix` なら指摘をワーカーに戻して直させ、再度検証する（`-MaxRepairs`、既定1回）。
解消しなければ打ち切り、報告に `[自己検証: 要確認]` を付け、残った指摘をカードの
コメントに残す。`-NoVerify` で無効にできる。

検証エージェントは、`TODO` のまま・本文の途中切れ・説明のない空欄・
報告と実物の食い違いを実測で検出できている。

## 割り込みの受け方

| ユーザーの操作 | ワーカーの反応 |
|---|---|
| 実行中から他の列へドラッグ | `cancel_requested` が立ち、次の区切りで停止。列はユーザーが移した先のまま |
| 「作業を中止」ボタン | 同上 |
| カードにコメント | 次回実行時に未読分を読み、最優先の指示として下書きに反映 |
| 下書き欄を編集 | `user_edited` は上書きされない。次回はそれを土台にする |

中止すると `cancel_requested` とリースは解除されるので、`要対応` に戻せば再開できる。

## 落ちたときの復旧

`agent_lease_until` を過ぎた `実行中` のカードは、次のワーカーが回収して処理し直す。
処理中に例外が出た場合はリースを外して `要対応` に戻し、理由を作業ログに残す。

## 進捗の見せ方

- `task_activity` … カードごとの作業ログ（開始・経過・生成中・完了・エラー・中止）
- `worker_state` … ワーカーの死活と現在の作業（1行のみ）

カンバンのヘッダがワーカーの状態を、カード詳細が作業ログを表示する。
`worker_state` の更新が 90 秒以上止まっていると、UI 側は「エラー（応答なし）」として扱う。

## ハマりどころ

`"=?UTF-8?B?$b64?="` は空文字になる。PowerShell は `?` を変数名の一部として取り込むため、
`$b64?` という未定義変数として解決される。`${b64}` と括ること。
これを踏んだ結果、日本語件名のメールがすべて件名なしで生成されていた。

## 権限と検証の確認結果

隔離したDBで一連の流れを実測した。

**承認して実行:** 「ディスク使用状況レポート」を依頼 → ワーカーが `run_command` を要求して停止
→ カンバンに実行するコマンドが全文表示される → 許可 → 実行 → `report.md` を作成
→ 自己検証「問題なし」 → レビュー待ちへ。レポートの数値は `Get-PSDrive` の実測値と一致した。

**拒否したとき:** 「インストール済みソフト一覧」を依頼 → コマンド実行を拒否
→ ワーカーは手順書と空の表を作り、未取得の理由を明記
→ 検証が「依頼の核心が未達」と指摘 → 修正を試みる → 再度拒否
→ 1回の上限で打ち切り、`[自己検証: 要確認]` を付けて残った指摘をコメントに記録。

**検証エージェント単体:** `TODO` のまま・「ここに記載」・本文の途中切れ・説明のない空欄・
報告と実物の食い違いを、いずれも `severity=high` として検出した。

## 実データでの確認結果

実際の通知から作られたカードに対して実行し、以下を確認した。

- 下書きが生成され、カードが `レビュー待ち` に移動する
- ワーカーが「返信相手が存在しない通知」を認識し、送信文ではなく対応メモの形にした
- 前提と限界（何が判別できなかったか、人間側で必要な操作）を `notes` に列挙し、
  カードのコメントとして残した

つまり、通知単体では文脈が足りないという Phase 1 の結論は下書きの質にも表れている。
Slack / メールの本文を正規 API で取得できれば、ここが改善する見込み。
